# Architect (yr)

Sketch types, function signatures, and module boundaries first. Implementation happens later in **poteto-mode-yr**, against this design.

This is the slim version of pstack's `architect`. It runs in one agent. It does not spawn subagents and does not run `arena-yr` unless the user opts in at Phase C.

## Modes

| Mode | When | Output |
|---|---|---|
| `ground-up` | A new project. | `architecture.md`, approved and installed packages, tooling, and the code skeleton. |
| `design-only` | An existing codebase: a feature, a refactor or a bug fix that crosses a function or module boundary. | `architecture.md` only. **No skeleton and no stub code**, because an empty function in live code breaks builds and tests, and a stub of the target shape beside the old code is a parallel path. Types and signatures live in the document. The implementer writes them into the real files. |

The caller says which. If it does not, ask once.

## Inputs and outputs

Inputs:

- The change folder `openspec/changes/<name>/`: `proposal.md` and the delta specs. For a refactor or a bug fix there is no proposal. Use the behavior contract and the notes in `status.md`.
- The current specs in `openspec/specs/`, and the graph (`openspec/graph.md`, plus **graph-yr** `read` for existing code).
- The language and stack from the proposal's Scope. This pack's environment setup assumes Python. If the proposal needs another stack, tell the user before going on.

Output: `openspec/changes/<name>/architecture.md`, shaped by [`references/architecture-template.md`](references/architecture-template.md).

If the sketch shows that a requirement is wrong or missing, stop and go back to **propose-yr**. Do not edit the requirements to fit the design.

## Start

Open a task list with one entry per phase: Ground, Sketch, Agree, then (ground-up only) Packages, Skeleton, then Hand off.

## Phase A: Ground

- **Ground-up**: skip this phase.
- **Existing code**: read the graph with **graph-yr** `read` over every subsystem the change touches. Naming a file is not grounding. Use **how-yr** only for what the graph cannot show, such as runtime behavior. If the design changes ownership or layering, also run **why-yr** on the existing shape, so the old rationale becomes a constraint and not a guess.

## Phase B: Sketch (one pass, you do it)

1. **Usage first.** Write the caller's view: a short quickstart and two or three realistic call sites. The usage is the spec. The types serve it.
2. **Data structures first.** Pick the core types. Trace each dominant access pattern through them. "We will add a map or cache later" means the structure is wrong. Follow **principle-model-the-domain-yr**, **principle-foundational-thinking-yr** and **principle-type-system-discipline-yr**.
3. **Design it twice.** Write two structurally distinct candidate shapes, each a short sketch of types, signatures and module map. Whole-shape alternatives, not point fixes (**principle-exhaust-the-design-space-yr**). Do this yourself, in this one agent.
4. **Screen** each candidate against [`references/design-red-flags.md`](references/design-red-flags.md). Assume the next contributor is an agent that sees only the files it opened, copies the nearest example, and takes the shortest path that compiles. Prefer the design where a change that looks right from one file is right for the whole repo.
5. **Compare on interface depth.** Prefer the design that hides more complexity behind a smaller public surface.
6. **Pick one** and write `architecture.md`. Put the loser in "Alternatives considered" with one line on why it lost. Leave the "Synthesis decision" section empty unless arena runs.

7. **Reference architectures.** If the proposal describes an event-driven service that consumes events, read [`references/micro-service-architecture.md`](references/micro-service-architecture.md) before you sketch. It is the author's usual layout and rules for such a service. Use it as a starting point for the candidates. Adopt, adapt or reject it, and record which and why in `architecture.md`. The same applies to any similar shape that the reference fits.

Principles that apply here: **principle-boundary-discipline-yr**, **principle-separate-before-serializing-shared-state-yr**, **principle-make-operations-idempotent-yr**, **principle-laziness-protocol-yr**.

## Phase C: Agree (checkpoint, on by default)

Stop and show the user a short summary in Traditional Chinese: the usage sketch, the module map, the key types, the chosen shape against the rejected one, and the open questions. Then ask with `AskUserQuestion`:

- **Approve.** Go on.
- **Compare with arena.** Run **arena-yr** on this design task with [`references/runner-prompt.md`](references/runner-prompt.md) as each runner's prompt, and the proposal plus the Phase A artifacts as shared grounding. Replace the sketch with the synthesized design, fill in "Synthesis decision", then ask again. This is the optional multi-agent path.
- **Revise.** Take the user's comments as new evidence. Re-run Phase B. Do not write code yet.

If the user said at the start "no checkpoint", skip the question.

In `design-only` mode, commit `architecture.md` now: `docs: add architecture for <name>`. Then go to Phase F.

## Phase D: Packages (ground-up only)

1. List every third-party package the design needs, in a table: package, what it is for, the module that uses it, why the standard library is not enough, and the alternative you considered. Prefer fewer packages. Add test and tooling packages to a second table.
2. Ask the user to approve with `AskUserQuestion`: approve the list, or edit it. Ask which tooling to use as a multi-select: pytest (recommended), ruff, mypy.
3. After approval, install into the venv with the venv's Python by path: `"<venv-python>" -m pip install <packages>`. If one fails, report the package and the Python version. The cause is often a newest Python with no prebuilt wheel. Let the user pick: another package, or a lower Python for the project.
4. Write the packages with their installed versions into `requirements.txt` as `name==version`, top-level packages only. Tooling goes into `requirements-dev.txt` the same way, after its `-r requirements.txt` line. Read the versions with `"<venv-python>" -m pip freeze` or `-m pip show <name>`.
5. Record in `architecture.md` the "Packages" and "Tooling" sections, and in `status.md` the `test`, `lint` and `typecheck` commands and the Python version.

## Phase E: Skeleton (ground-up only)

Write the skeleton so it is the contract for implementation:

- Real files in the real layout: types, signatures, module boundaries, entry points, minimal package and test config.
- Stub bodies that raise `NotImplementedError`. Pseudocode comments only for tricky logic. Doc comments state intent and invariants, not narration.
- One test function per scenario in the delta specs, named `test_<scenario name in snake_case>`, whose body is `pytest.skip("not implemented")`. This is the implementation checklist, and **archive-yr** checks it later. Skip this when the user did not choose pytest. If you adopted a reference architecture, add what its "For the skeleton" section lists.
- Boundaries are visible: a reader can trace data from input to output by reading types and signatures alone.

Then run the build check: the type checker if the user chose one, otherwise `"<venv-python>" -m compileall -q <source folder>`. The skeleton must build. Run the test command: all tests must pass or skip.

Commit it as its own commit, "scaffold first" (**principle-foundational-thinking-yr**): `chore: scaffold <name>`. Commit `architecture.md`, `requirements.txt` and the status file in their own commits before it.

## Phase F: Hand off

Report in a few sentences: where `architecture.md` is, the chosen shape, the packages, open questions. The next step is the work branch and **poteto-mode-yr**.

## During implementation (rules the implementer follows)

The design is the contract. A deviation is a signal to surface, not friction to absorb.

- If a function needs a parameter the sketch did not anticipate, ask whether the sketch was wrong, a requirement was missed, or the implementation is overreaching.
- Before closing a unit, compare accepted deviations with the saved contracts. Once the user or the review accepts a change, update `architecture.md` ("Implementation reconciliation") and the affected signatures. Record who accepted it. Keep unaccepted changes visible.
- A local deviation that leaves the shared contract intact needs one line saying why the design still holds.
- One deviation needs no approval: where a playbook of **poteto-mode-yr** conflicts with this document, the playbook wins. The implementer records it in "Implementation reconciliation" and updates this document to match.

## When the architecture is wrong (scrap)

If implementation keeps producing friction the sketch cannot absorb, throw the sketch out. Do not bolt fixes onto a wrong design (**principle-redesign-from-first-principles-yr**, **principle-fix-root-causes-yr**).

The signal is a pattern, not one instance:

- The same workaround shape appears repeatedly in unrelated code.
- Several unrelated edge cases each need a special-case branch.
- Types need escape hatches (`Any`, casts, optional fields always set in practice) to compile.
- The "we need a lock" reflex shows up where the sketch said state was not shared.
- Callers must know the abstraction's internal rules to use it.
- Two or more independent deviations have the same shape.

A few edge cases do not condemn an architecture. When you scrap: re-read the graph over what is built, redesign as if the new constraints were day-one assumptions, subtract before adding (**principle-subtract-before-you-add-yr**), and return to Phase B. Tell the user before you do.

# Architecture template

File: `openspec/changes/<name>/architecture.md`. English. The design and its rationale, with the type sketch. One page. Sentence-case headings, no boilerplate. Replace the italic notes with actual content.

## Problem

*One paragraph. What we're trying to do, and what about the existing system or constraints makes the shape non-obvious. If [Phase A](../SKILL.md) surfaced constraints the design must honor (existing types to interop with, callers we can't break, invariants that crossed our boundary), name them here so the reader sees the same constraints you saw.*

## Usage (caller's view)

*Write this first, before the type sketch. Show the README or quickstart the consumer reads, plus two or three realistic call sites in their own code. What they import, what they call, what comes back. The type sketch in [Shape](#shape) is derived from this. The two must agree. When they diverge, reconcile the sketch to the usage, not the reverse. The caller's experience is the spec. The types serve it.*

## Shape

*The recommended architecture. Data structures first. Then how data flows through the signatures. Name the load-bearing decisions. State which invariants are encoded in types, where validation lives, and what the system deliberately does not do. Judge interface depth explicitly. State what complexity the public surface hides, what remains exposed to callers, and why the interface is no larger than needed. Cite the principle behind each decision (e.g., `per boundary-discipline`). Don't restate it.*

## Synthesis decision

*Filled in by [arena](../../arena-yr/SKILL.md). Records which candidate became the base and why, what was adapted from each of the others, and what was rejected and why.*

## Tradeoffs accepted

*One bullet per tradeoff the chosen shape makes. Form: "we accept X in exchange for Y." Name anything a future reader might mistake for an oversight, including things that look like premature optimization or premature simplification.*

## Alternatives considered

*Required. Name at least one concrete alternative shape, with one line on why it lost. Judge each alternative on interface depth, not implementation simplicity alone. Name the complexity it exposes to callers and the complexity it hides. Two or three alternatives belong here when the design space had real contenders. One is fine when the constraints forced the answer, with the conclusion phrased as "this was the only viable shape because..." Avoid listing flavors of the same shape. This section covers design alternatives the chosen shape considered and rejected, not other runner candidates.*

## Implementation reconciliation

*During implementation, record accepted deviations and their acceptance sources here, and update the affected usage, outcome contracts, signatures, and ownership in this design. Record why local deviations leave the shared contract valid. Keep unaccepted changes unresolved. Reconcile before closing a unit or handing its contract to the next worker.*

## Open questions and risks

*Things you noticed during the sketch that the human needs to weigh in on, and risks worth flagging before implementation starts. Phrase as questions, not assertions, so the human's answer is the resolution rather than a comment.*

## Packages (new project only)

*A table: package, what it is for, which module uses it, why the standard library is not enough, alternative considered. Written before anything is installed, and approved by the user.*

## Tooling (new project only)

*The Python version found in the environment, the test command, and the lint and type-check commands if any. These go into the status file too.*

## Service contract (only when a reference architecture for an event-driven service is used)

*The event types and their models, the disposition table (outcome to ack or nack, with the retry bound), the idempotency key, the thread pool size, the broker prefetch and the shutdown limit, and what is async and what is threaded. See `micro-service-architecture.md`.*

## Next implementation step

*The first thing to build against the sketch. One sentence. What you'd start writing immediately after synthesis (or after Phase D sign-off, if a checkpoint was opted into).*

# Design red flags

Screen every candidate before synthesis. A red flag is a reason to revise or reject the shape.

## Shallow module

A shallow module exposes a large interface while hiding little complexity. Judge depth by the capability and policy hidden behind the public surface relative to the size of that surface. Prefer a simple interface backed by substantial behavior.

Do not confuse a deep module with a deep call chain. A deep call chain scatters understanding across layers. A deep module concentrates capability behind one interface.

Look for these signs:

- Callers coordinate several methods to complete one operation.
- Public options expose internal stages or implementation choices.
- Learning the interface does not save the caller from learning the implementation.

## Information leakage

Information leakage makes multiple modules depend on the same internal decision. A representation, policy, or protocol detail appears in more than one place, so changing it requires coordinated edits.

Public re-exports of transport or wire types are leakage. Parse external data into domain types behind the interface. Keep storage schemas, framework objects, and protocol details private.

## Temporal decomposition

Temporal decomposition organizes modules by execution order instead of the knowledge they own. Separate load, validate, transform, and save stages often repeat one representation and its invariants across several boundaries.

Group code around domain knowledge and ownership. Methods that run at different times can still belong to one module when they protect the same decisions.

## Pass-through method

A pass-through method forwards the same arguments to another method with the same shape. It adds a layer without hiding complexity.

Remove it or move responsibility to the module that can complete the operation. Keep a forwarding boundary only when it adds policy, adaptation, or a distinct abstraction.

## Split ownership

More than one module writes the same state or keeps its own copy of it. An agent that edits one writer can't see the others, so their rules diverge.

Give each piece of state one owner. Other modules read it or ask the owner to change it.

## Two ways to do one task

The design supports more than one way to do the same task. An agent copies whichever way it finds first, so every way keeps gaining callers.

Keep one way. Move callers off the others and delete them in the same change.

## Importable internals

A caller can import a module's internals. An agent takes the shortest path that compiles, so it imports them directly and they become part of the interface.

Make internals unreachable from outside the module, so an import from outside fails the build.

## Hand-synced list

Two or more places list the same items, and adding an item means editing every list. An agent that sees one list updates only that one.

Keep one list and derive the others from it. If a list can't be derived, make the build fail when the lists disagree.

# Reference architecture: event-driven micro-service (Python)

A proven shape for a service that consumes events from a broker, may expose an API, and runs each event on its own thread. It is the author's usual layout. It is a **reference**, not a rule. Use it when the proposal describes a service of this kind, or something close. Adopt it, adapt it, or reject it, and record the choice in `architecture.md` (under "Shape", with the reason, and under "Alternatives considered" if you reject it).

Read it fully before you sketch. Then write a `## Service contract` section in `architecture.md` (see the end of this file).

## Layout

Each file has one job. Imports point one way only: down this list.

| Layer | Owns | Must not |
|---|---|---|
| `main.py` | Composition root. Loads config, builds the clients and the worker, starts them, handles signals and shutdown. | Hold any business logic or a `try/except` for events. |
| `worker.py` | The flow for one event: parse, call helpers, map the outcome to ack or nack. All exception handling for events. The only file that touches the broker's ack and nack. | Hold domain rules. Those go to `helper.py`. |
| `helper.py` | Internal logic. Pure functions and small classes that take models and injected clients, and return results or raise typed errors. | Import `worker` or `main`. Ack or nack. Read environment variables. |
| `models.py` | Data shapes: event payloads, results, domain types. | Import any other file of this service. |
| `common/` | Shared tools with no domain knowledge: logging setup, retry and backoff, the error types, small utilities. | Know about events or the broker's payloads. |
| `config/` | Typed settings, loaded once at startup from the environment or a file, then injected. | Be read from anywhere except `main.py`. |

Import direction: `main` → `worker` → `helper` → `models`. `common` and `config` are leaves that any layer above may import. Nothing imports upward.

Grow by splitting inside a layer (`helper/` as a package, one file per capability), never by adding a new layer. Keep `common/` honest: a utility moves in only when two or more modules use it (**principle-laziness-protocol-yr**, **principle-minimize-reader-load-yr**).

## Design rules

1. **Data shapes first.** Name the event payloads and results in `models.py` before any logic. Use typed models, and make invalid states unrepresentable (**principle-model-the-domain-yr**, **principle-type-system-discipline-yr**).
2. **Parse at the boundary.** `worker.py` parses the raw message into a model once. A message that does not parse is a permanent error, and it is never retried. Everything below trusts the types (**principle-boundary-discipline-yr**).
3. **Config is injected.** `config/` builds one frozen settings object at startup and fails fast on a missing or invalid value. `main.py` passes it, or the clients built from it, into the worker and helpers. Nothing else reads `os.environ`. Never log secrets (**principle-boundary-discipline-yr**).
4. **Business logic stays pure.** `helper.py` gets its inputs as arguments, so it tests without a broker (**principle-boundary-discipline-yr**, **principle-test-behavior-not-implementation-yr**).
5. **The outcome of an event is a decision, and it is made once.** Define an error taxonomy in `common/` (for example `TransientError` and `PermanentError`) and a disposition table in `worker.py`:

   | Outcome | Disposition |
   |---|---|
   | Success | ack |
   | Permanent error (bad payload, rule violation) | nack without requeue, to the dead-letter path when the broker has one |
   | Transient error (timeout, dependency down) | nack with requeue, with a bounded retry count |
   | Unexpected exception | treat as transient up to the retry bound, then as permanent, and log it with the event id |

   Every event ends in exactly one ack or nack, including when the handler raises (**principle-model-the-domain-yr**).
6. **Handlers are idempotent.** A nack with requeue, a crash before the ack and a broker redelivery all run the handler again with the same event. Pick the idempotency key (usually the event id) and make a second run converge to the same end state (**principle-make-operations-idempotent-yr**).
7. **One event, one thread, nothing shared.** Each event runs on its own thread, and everything it mutates is created inside that thread's call. No mutable module-level state. Shared objects are limited to clients that are documented thread-safe, or each thread builds its own. Eliminate sharing before you reach for a lock (**principle-separate-before-serializing-shared-state-yr**).
   - **Bound it.** One thread per event still needs a cap. Run the threads in a pool sized from config, and tie the broker prefetch to the same number, so a burst of events cannot create unlimited threads (**principle-foundational-thinking-yr**).
   - **Ack from the right thread.** Many broker clients are not thread-safe. Check the client's documentation. If the ack or nack must run on the connection's thread, hand it back through the library's thread-safe call or a queue. Do not call it from the event thread by default.
   - **Shut down cleanly.** On a stop signal, stop taking new events, let the in-flight threads finish within a time limit from config, nack what did not finish so the broker redelivers it, then close the clients.
8. **API flows are async.** Handlers and outbound HTTP calls use `async def` and an async client. A blocking call inside a coroutine stalls the whole loop, so a blocking library goes through `run_in_executor` or a thread. Event threads are synchronous by default. If an event thread must call an async function, run it with `asyncio.run` inside that thread. Never start a second loop on a thread that already has one. If the design needs the event threads and the API to share one loop, say so in `architecture.md` and get the user's agreement.
9. **Every log line carries the event id.** Set it once at the top of the event thread, in `worker.py`. Log the disposition and the duration at the end of each event.
10. **Encode the layering.** Add `tests/test_layers.py` from [`micro-service-layer-test.py`](micro-service-layer-test.py) and set its package name and layer order. The import direction, the rule that only `worker.py` acks, and the rule that only `config/` reads the environment then fail a test instead of relying on review (**principle-encode-lessons-in-structure-yr**, **principle-build-the-lever-yr**).

## What to write in `architecture.md`

Add a `## Service contract` section:

- The event types and their models.
- The disposition table (outcome to ack or nack, with the retry bound).
- The idempotency key.
- The thread pool size, the broker prefetch and the shutdown time limit, all from config.
- What is async and what is threaded.

## For the skeleton (ground-up mode)

- Create the files and folders of the layout, with stub bodies, plus `tests/test_layers.py`.
- Besides the one skipped test per scenario, add skipped tests for the checks below, so the implementer has a checklist.

## Checks to carry into the implementation

State these in `architecture.md` under "Next implementation step". The implementer runs them as part of verification (**principle-prove-it-works-yr**). If a throughput or latency number is reported, explain what limits it first (**principle-explain-the-number-yr**).

- **Disposition per outcome.** One test per row of the disposition table, asserting exactly one ack or nack.
- **Redelivery.** Feed the same event twice and assert the same end state.
- **Parallel events.** Run many events at once through the worker with a fake broker, and assert no state leaks between them and the pool cap holds.
- **Shutdown.** Stop during in-flight events and assert they finish or are nacked.
- **No blocking in the loop.** For API flows, assert a slow dependency does not delay other requests.
- **Build order.** Bottom-up: `models.py`, `config/`, `common/`, `helper.py`, `worker.py`, `main.py`. In multi-agent mode, the independent `helper` capabilities can run in parallel after the first three.

"""Layer test for a micro-service. Copy to tests/test_layers.py.

Set PACKAGE to the folder (or module prefix) that holds main.py, worker.py,
helper.py, models.py, common/ and config/. Import direction may only go down
ORDER. common and config are leaves that every layer may import.
Standard library only.
"""
import ast
from pathlib import Path

PACKAGE = "service"  # folder under the repo root or under src/
ORDER = ["main", "worker", "helper", "models"]
LEAVES = {"common", "config"}
BROKER_CALLS = {"ack", "nack", "basic_ack", "basic_nack", "reject"}


def _root():
    here = Path(__file__).resolve().parent.parent
    for cand in (here / "src" / PACKAGE, here / PACKAGE):
        if cand.is_dir():
            return cand
    raise AssertionError(f"package folder '{PACKAGE}' not found")


def _layer_of(path, root):
    rel = path.relative_to(root)
    first = rel.parts[0]
    name = first[:-3] if first.endswith(".py") else first
    return name


def _imported_layers(tree, pkg_prefix):
    found = set()
    for node in ast.walk(tree):
        if isinstance(node, ast.ImportFrom):
            if node.level == 1 and node.module:
                found.add(node.module.split(".")[0])
            elif node.level == 1 and not node.module:
                found.update(a.name.split(".")[0] for a in node.names)
            elif node.level == 0 and node.module and node.module.split(".")[0] == pkg_prefix:
                parts = node.module.split(".")
                if len(parts) > 1:
                    found.add(parts[1])
                else:
                    found.update(a.name.split(".")[0] for a in node.names)
        elif isinstance(node, ast.Import):
            for a in node.names:
                parts = a.name.split(".")
                if parts[0] == pkg_prefix and len(parts) > 1:
                    found.add(parts[1])
    return found


def test_imports_only_point_down():
    root = _root()
    problems = []
    for path in sorted(root.rglob("*.py")):
        layer = _layer_of(path, root)
        if layer in LEAVES and layer not in ORDER:
            allowed = LEAVES
        elif layer in ORDER:
            allowed = set(ORDER[ORDER.index(layer) + 1:]) | LEAVES | {layer}
        else:
            continue
        tree = ast.parse(path.read_text(encoding="utf-8"))
        for target in _imported_layers(tree, root.name):
            if (target in ORDER or target in LEAVES) and target not in allowed:
                problems.append(f"{path.relative_to(root)}: {layer} must not import {target}")
    assert not problems, "\n".join(problems)


def test_only_worker_acks():
    root = _root()
    problems = []
    for path in sorted(root.rglob("*.py")):
        if _layer_of(path, root) == "worker":
            continue
        tree = ast.parse(path.read_text(encoding="utf-8"))
        for node in ast.walk(tree):
            if isinstance(node, ast.Call) and isinstance(node.func, ast.Attribute) and node.func.attr in BROKER_CALLS:
                problems.append(f"{path.relative_to(root)}:{node.lineno}: ack or nack outside worker")
    assert not problems, "\n".join(problems)


def test_only_config_reads_environment():
    root = _root()
    problems = []
    for path in sorted(root.rglob("*.py")):
        if _layer_of(path, root) in ("config", "main"):
            continue
        tree = ast.parse(path.read_text(encoding="utf-8"))
        for node in ast.walk(tree):
            if isinstance(node, ast.Attribute) and node.attr in ("environ", "getenv") and isinstance(node.value, ast.Name) and node.value.id == "os":
                problems.append(f"{path.relative_to(root)}:{node.lineno}: environment read outside config")
    assert not problems, "\n".join(problems)

# Architect runner prompt

The orchestrator passes this file through to every parallel candidate runner during Phase B and fills in the variable inputs around it: the task, the Phase A grounding artifacts, the isolated working directory, and the path to write outputs. The working directory is a git worktree when available, otherwise a per-runner subdirectory under the sketch dir. What matters is independence between candidates.

You are producing one candidate design in architect's parallel exploration. Read the **architect-yr** skill in full first. That's the workflow you're inside. Output a candidate design package: type sketch, function signatures, module map, and prose rationale shaped per [`architecture-template.md`](architecture-template.md).

Apply the following discipline. The orchestrator compares candidates on these axes to pick a base.

- Caller's usage first. Write the README-style usage and two or three real call sites before the types, then derive the type sketch from them. The usage is the spec. The two must agree, so reconcile the sketch to the usage, not the reverse.
- Data structures first. Get the core types right and the code becomes obvious. Trace each dominant access pattern through the proposed structure. If the answer is "we'll add a map / index / cache later," the structure is wrong.
- Interface depth. Compare the capability hidden behind the public surface relative to the size of that surface. Prefer a simple interface that pulls complexity into the callee, even when the implementation becomes less simple. Do not put transport or wire types on the public API. Parse into domain types behind the interface.
- Shared state: if two actors might both write, ask "what happens?" If the answer isn't "nothing," default to per-actor state with a merge at the read boundary, per the **principle-separate-before-serializing-shared-state-yr** skill.
- Make boundaries visible. `not implemented` errors for bodies, `// TODO` pseudocode for tricky logic, doc comments stating intent and invariants. A reader should trace data from input to output by reading types and signatures alone.

# Archive (yr)

Close a change. The deltas become part of the current specs, and the change folder moves to `openspec/changes/archive/<date>-<name>/`.

The merge is done by a script, `scripts/openspec_archive.py`, so the result does not depend on how carefully a model edits a file. Use the project's venv Python or any Python 3. The script uses only the standard library.

Run it from the repo root with the path of this skill's folder: `"<python>" "<this skill's folder>/scripts/openspec_archive.py" <command> ...`.

## Step 1. Which kind of change

- **With deltas** (`openspec/changes/<name>/specs/` exists): a feature or a new project. Do all steps.
- **Without deltas** (a bug fix or a refactor): skip Steps 2 and 3. Go to Step 4. The folder still moves, so the status and the notes stay in the history.

## Step 2. Reconcile the scenarios with the code

1. Validate the deltas: `validate openspec/changes/<name>`. Fix errors.
2. Check the tests: `check openspec/changes/<name> --tests tests` (add other test folders if the project has them). It reports scenarios with no `test_<scenario name>` and tests that still skip.
3. Show the user the report. For each missing or skipped scenario, choose with the user: write the test now, or keep the scenario and note why it has no test, or drop the scenario from the delta because the behavior changed. Do not archive a scenario you know is false.
4. If the implemented behavior differs from the delta, edit the delta so it describes what was built, and tell the user what changed. The spec must match the code.

## Step 3. Record the outcome

Append to `openspec/changes/<name>/proposal.md`:

```markdown
## Outcome
- Finished: <date>
- Branch: <branch>
- Review report: openspec/reviews/<name>.md
- Differences from the plan: <one to three lines, or "none">
- Scenarios without a test: <list with the reason, or "none">
```

## Step 4. Apply

1. Dry run: `apply openspec/changes/<name> --specs openspec/specs --archive openspec/changes/archive --dry-run`. Show the user which specs are created or updated.
2. Run the same command without `--dry-run`. It validates everything first and writes nothing on an error. An error such as "ADDED requirement already exists" means the name collides with the spec: change the delta to MODIFIED, or rename.
3. Commit: `docs: archive <name>`. Stage `openspec/` only.

## If a spec conflicts later

If landing hits a git conflict in a spec file, `remerge` replays the archived deltas onto the other side's spec without moving anything. See the Landing playbook of **poteto-mode-yr**.

## Step 5. Report

Say which specs changed, where the change folder went, and the scenario coverage. Hand back to the caller. The next step is landing the branch.

#!/usr/bin/env python3
"""Validate, check and archive an OpenSpec-style change. Standard library only.

Layout (relative to the repo root):
  openspec/specs/<domain>/spec.md                   current truth
  openspec/changes/<name>/proposal.md
  openspec/changes/<name>/specs/<domain>/spec.md    delta: ADDED / MODIFIED / REMOVED
  openspec/changes/archive/<date>-<name>/           finished changes

Commands:
  validate <change-dir>
      Check the delta files: headers, unique names, at least one scenario per
      requirement, SHALL or MUST in the requirement text.
  check <change-dir> --tests <tests-dir> [<tests-dir> ...]
      For every scenario in the delta, look for `def test_<slug>` in the tests.
      Reports missing tests and tests that still skip.
  apply <change-dir> --specs <specs-dir> --archive <archive-dir> [--date YYYY-MM-DD] [--dry-run]
      Merge the deltas into the specs, then move the change folder into the archive.
      Everything is validated in memory first. Nothing is written on an error.

  remerge <archived-change-dir> --specs <specs-dir> [--dry-run]
      Re-apply the deltas of an already archived change to the specs. Nothing is moved.
      Use it after a git conflict in a spec file.

Exit code 0 = ok, 1 = problems found, 2 = bad usage.
"""
import argparse
import datetime
import re
import shutil
import sys
from pathlib import Path

REQ_RE = re.compile(r"^### Requirement:[ \t]*(.+?)[ \t]*$")
SCN_RE = re.compile(r"^#### Scenario:[ \t]*(.+?)[ \t]*$")
H2_RE = re.compile(r"^## (.+?)[ \t]*$")
SECTIONS = ("ADDED", "MODIFIED", "REMOVED")


class SpecError(Exception):
    pass


def read(path):
    return Path(path).read_text(encoding="utf-8").replace("\r\n", "\n")


def slug(name):
    return re.sub(r"[^a-z0-9]+", "_", name.lower()).strip("_")


def split_blocks(lines):
    """Split lines into (preamble_lines, [(name, block_lines)]). A block starts at a
    requirement header and ends before the next requirement header or any `## ` header."""
    pre, blocks, cur_name, cur = [], [], None, []
    for line in lines:
        m = REQ_RE.match(line)
        if m or H2_RE.match(line):
            if cur_name is not None:
                blocks.append((cur_name, cur))
                cur_name, cur = None, []
            if m:
                cur_name, cur = m.group(1), [line]
                continue
        if cur_name is not None:
            cur.append(line)
        else:
            pre.append(line)
    if cur_name is not None:
        blocks.append((cur_name, cur))
    return pre, blocks


def split_spec(lines):
    """Split a current spec into (preamble, [(name, block)], tail). The tail is every
    `## ` section after the requirements, such as `## Notes`. It stays at the end."""
    pre, blocks, tail = [], [], []
    cur_name, cur, seen_req, in_tail = None, [], False, False
    for line in lines:
        if in_tail:
            tail.append(line)
            continue
        m, h = REQ_RE.match(line), H2_RE.match(line)
        if m:
            if cur_name is not None:
                blocks.append((cur_name, cur))
            cur_name, cur = m.group(1), [line]
            continue
        if h:
            title = h.group(1).strip().lower()
            if cur_name is not None or (seen_req and title != "requirements"):
                if cur_name is not None:
                    blocks.append((cur_name, cur))
                    cur_name, cur = None, []
                in_tail = True
                tail.append(line)
                continue
            if title == "requirements":
                seen_req = True
        (cur if cur_name is not None else pre).append(line)
    if cur_name is not None:
        blocks.append((cur_name, cur))
    return pre, blocks, tail


def trim(block):
    out = list(block)
    while out and not out[-1].strip():
        out.pop()
    return out


def parse_delta(path):
    """Return {'purpose': str|None, 'ADDED': [(name, lines)], 'MODIFIED': [...], 'REMOVED': [...]}"""
    text = read(path)
    lines = text.split("\n")
    result = {"purpose": None, "ADDED": [], "MODIFIED": [], "REMOVED": []}
    sections, cur, buf = [], None, []
    for line in lines:
        m = H2_RE.match(line)
        if m:
            if cur is not None:
                sections.append((cur, buf))
            cur, buf = m.group(1).strip(), []
        elif cur is not None:
            buf.append(line)
    if cur is not None:
        sections.append((cur, buf))
    for title, body in sections:
        if title.lower() == "purpose":
            result["purpose"] = "\n".join(body).strip()
            continue
        m = re.match(r"^(ADDED|MODIFIED|REMOVED)\s+Requirements$", title, re.I)
        if not m:
            raise SpecError(f"{path}: unknown section '## {title}'. Allowed: Purpose, ADDED Requirements, MODIFIED Requirements, REMOVED Requirements")
        _, blocks = split_blocks(body)
        result[m.group(1).upper()].extend((n, trim(b)) for n, b in blocks)
    return result


def scenarios_of(block_lines):
    return [m.group(1) for m in (SCN_RE.match(l) for l in block_lines) if m]


def validate_delta(path):
    errs, warns = [], []
    try:
        d = parse_delta(path)
    except SpecError as e:
        return [str(e)], []
    names = [n for sec in SECTIONS for n, _ in d[sec]]
    for n in sorted({n for n in names if names.count(n) > 1}):
        errs.append(f"{path}: requirement '{n}' appears more than once")
    scn = []
    for sec in ("ADDED", "MODIFIED"):
        for name, block in d[sec]:
            ss = scenarios_of(block)
            if not ss:
                errs.append(f"{path}: requirement '{name}' ({sec}) has no '#### Scenario:'")
            if not re.search(r"\b(SHALL|MUST)\b", "\n".join(block)):
                warns.append(f"{path}: requirement '{name}' has no SHALL or MUST")
            scn.extend(ss)
    for s in sorted({s for s in scn if scn.count(s) > 1}):
        errs.append(f"{path}: scenario '{s}' appears more than once")
    slugs = {}
    for s in scn:
        slugs.setdefault(slug(s), []).append(s)
    for k, v in slugs.items():
        if len(set(v)) > 1:
            errs.append(f"{path}: scenarios {v} give the same test name test_{k}")
    if not any(d[s] for s in SECTIONS):
        errs.append(f"{path}: delta has no requirements")
    return errs, warns


def delta_files(change):
    root = Path(change) / "specs"
    return sorted(root.glob("*/spec.md")) if root.is_dir() else []


def merge_spec(domain, spec_text, delta):
    """Return the new spec text. Raises SpecError on conflicts."""
    if spec_text is None:
        if delta["MODIFIED"] or delta["REMOVED"]:
            raise SpecError(f"{domain}: spec does not exist yet, so it cannot have MODIFIED or REMOVED requirements")
        purpose = delta["purpose"] or "TBD"
        pre = [f"# {domain} Specification", "", "## Purpose", purpose, "", "## Requirements"]
        blocks, tail = [], []
    else:
        lines = spec_text.split("\n")
        pre, blocks, tail = split_spec(lines)
        pre = list(pre)
        if not any(re.match(r"^## Requirements\s*$", l) for l in pre):
            pre += ["", "## Requirements"]
    index = {n: i for i, (n, _) in enumerate(blocks)}
    blocks = [(n, trim(b)) for n, b in blocks]
    for name, block in delta["REMOVED"]:
        if name not in index:
            raise SpecError(f"{domain}: REMOVED requirement '{name}' not found in the spec")
    for name, block in delta["MODIFIED"]:
        if name not in index:
            raise SpecError(f"{domain}: MODIFIED requirement '{name}' not found in the spec")
    for name, block in delta["ADDED"]:
        if name in index:
            raise SpecError(f"{domain}: ADDED requirement '{name}' already exists. Use MODIFIED")
    removed = {n for n, _ in delta["REMOVED"]}
    modified = dict(delta["MODIFIED"])
    out = []
    for name, block in blocks:
        if name in removed:
            continue
        out.append((name, modified.get(name, block)))
    out.extend(delta["ADDED"])
    text = "\n".join(trim(pre)) + "\n"
    for _, block in out:
        text += "\n" + "\n".join(block) + "\n"
    tail = trim(tail)
    if tail:
        text += "\n" + "\n".join(tail) + "\n"
    return text


def cmd_validate(a):
    files = delta_files(a.change)
    if not files:
        print(f"No delta files under {a.change}/specs/*/spec.md")
        return 1
    bad = 0
    for f in files:
        errs, warns = validate_delta(f)
        for w in warns:
            print("warning:", w)
        for e in errs:
            print("error:", e)
        bad += len(errs)
    print("valid" if not bad else f"{bad} error(s)")
    return 1 if bad else 0


def cmd_check(a):
    files = delta_files(a.change)
    tests = {}
    for t in a.tests:
        for p in sorted(Path(t).rglob("*.py")) if Path(t).is_dir() else []:
            tests[p] = read(p)
    missing, skipped, ok = [], [], 0
    for f in files:
        d = parse_delta(f)
        for sec in ("ADDED", "MODIFIED"):
            for name, block in d[sec]:
                for sc in scenarios_of(block):
                    fn = f"test_{slug(sc)}"
                    pat = re.compile(rf"^[ \t]*(?:async[ \t]+)?def {re.escape(fn)}\b", re.M)
                    found = [(p, t) for p, t in tests.items() if pat.search(t)]
                    if not found:
                        missing.append((f.parent.name, sc, fn))
                        continue
                    p, t = found[0]
                    m = pat.search(t)
                    start = m.start()
                    nxt = re.search(r"^(?:@|def |async def |class )", t[m.end():], re.M)
                    body = t[max(0, start - 200): m.end() + (nxt.start() if nxt else len(t))]
                    if re.search(r"pytest\.skip\(|mark\.skip\b|unittest\.skip|NotImplementedError", body):
                        skipped.append((f.parent.name, sc, fn))
                    else:
                        ok += 1
    print(f"scenarios with a passing-shape test: {ok}")
    for dom, sc, fn in missing:
        print(f"missing: [{dom}] '{sc}' -> {fn}")
    for dom, sc, fn in skipped:
        print(f"still skipped: [{dom}] '{sc}' -> {fn}")
    return 1 if (missing or skipped) else 0


def cmd_apply(a):
    change = Path(a.change)
    if not change.is_dir():
        print(f"Not a folder: {change}")
        return 2
    specs, archive = Path(a.specs), Path(a.archive)
    date = a.date or datetime.date.today().isoformat()
    target = archive / f"{date}-{change.name}"
    if target.exists():
        print(f"Archive target exists: {target}")
        return 1
    files = delta_files(change)
    writes = []
    all_errs = []
    for f in files:
        errs, _ = validate_delta(f)
        all_errs += errs
    if all_errs:
        for e in all_errs:
            print("error:", e)
        return 1
    try:
        for f in files:
            domain = f.parent.name
            spec_path = specs / domain / "spec.md"
            old = read(spec_path) if spec_path.exists() else None
            writes.append((spec_path, merge_spec(domain, old, parse_delta(f)), old is None))
    except SpecError as e:
        print("error:", e)
        return 1
    for p, _, new in writes:
        print(("create " if new else "update ") + str(p))
    print(f"move {change} -> {target}")
    if a.dry_run:
        print("dry run: nothing written")
        return 0
    for p, text, _ in writes:
        p.parent.mkdir(parents=True, exist_ok=True)
        p.write_text(text, encoding="utf-8", newline="\n")
    archive.mkdir(parents=True, exist_ok=True)
    shutil.move(str(change), str(target))
    print("done")
    return 0


def cmd_remerge(a):
    """Re-apply the deltas of an archived change to the specs, without moving anything.
    Used after a git conflict in a spec file: take the other side's spec, then run this."""
    files = delta_files(a.change)
    if not files:
        print(f"No delta files under {a.change}/specs/*/spec.md")
        return 1
    writes = []
    try:
        for f in files:
            domain = f.parent.name
            spec_path = Path(a.specs) / domain / "spec.md"
            old = read(spec_path) if spec_path.exists() else None
            writes.append((spec_path, merge_spec(domain, old, parse_delta(f)), old is None))
    except SpecError as e:
        print("error:", e)
        return 1
    for p, text, new in writes:
        print(("create " if new else "update ") + str(p))
        if not a.dry_run:
            p.parent.mkdir(parents=True, exist_ok=True)
            p.write_text(text, encoding="utf-8", newline="\n")
    print("dry run: nothing written" if a.dry_run else "done")
    return 0


def main(argv):
    ap = argparse.ArgumentParser(description=__doc__, formatter_class=argparse.RawDescriptionHelpFormatter)
    sub = ap.add_subparsers(dest="cmd", required=True)
    v = sub.add_parser("validate"); v.add_argument("change"); v.set_defaults(fn=cmd_validate)
    c = sub.add_parser("check"); c.add_argument("change"); c.add_argument("--tests", nargs="+", required=True); c.set_defaults(fn=cmd_check)
    p = sub.add_parser("apply"); p.add_argument("change"); p.add_argument("--specs", required=True)
    p.add_argument("--archive", required=True); p.add_argument("--date"); p.add_argument("--dry-run", action="store_true"); p.set_defaults(fn=cmd_apply)
    r = sub.add_parser("remerge"); r.add_argument("change"); r.add_argument("--specs", required=True); r.add_argument("--dry-run", action="store_true"); r.set_defaults(fn=cmd_remerge)
    a = ap.parse_args(argv)
    try:
        return a.fn(a)
    except SpecError as e:
        print("error:", e)
        return 1


if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))

# Arena

Open a todolist with one entry per phase (Frame, Fan out, Cross-judge, Pick, Graft, Verify) before launching anything.

## Phase A: Frame

Every candidate gets the same prompt, so the prompt is the contract.

1. State the artifact each candidate is producing.
2. Derive the rubric, 3-6 concrete gradeable criteria for what success looks like on *this* task. It is the picker's tool in Phase D. Candidates only see the task.
3. Pick the runners. Default to three runners on the session model, with diversity coming from distinct design directions in the task framing. If the user names models, set `model` per runner, otherwise omit `model`. Spawn more runners when the arena covers more design directions. Give each runner the same prompt.
4. Give each candidate its own output location (a git worktree where possible, otherwise `/tmp/arena-<slug>/candidate-<n>/`), per the **principle-separate-before-serializing-shared-state-yr** skill.

## Phase B: Fan out

Spawn all N subagents in one message with `run_in_background: true`, each with the task, the path to the shared grounding, its own output path, and instructions to produce the artifact and a short rationale naming the alternatives it considered and what it rejected.

If a candidate produces no output, proceed with N-1 and note the dropout.

## Phase C: Cross-judge

After all Phase B candidates complete, spawn one readonly judge subagent on the session model (or a model the user names). It sees the rubric and the candidates by path label, scores each criterion, and recommends a base with rationale. It runs in parallel with your reading in Phase D. Don't spawn it while candidates are still writing.

## Phase D: Pick a base

Read every candidate end to end before picking. Score each against the rubric criterion by criterion, not on holistic feel, and compare with the cross-judge. Agreement on the base confirms the pick. Disagreement means one of you is biased or the rubric was ambiguous. Read both rationales before deciding.

Pick the base a future maintainer can extend most easily without breaking invariants. When two feel tied, prefer the cleaner boundary or smaller API, per the Laziness Protocol.

## Phase E: Graft

Walk each losing candidate once more for what is worth porting into the base, usually one or two things per candidate, not most of it. Fold each graft in by hand, per the **principle-redesign-from-first-principles-yr** skill, so the result stays coherent under one mental model. Don't paste mechanically.

If the candidates converge on one shape, that is strong agreement. Note it and ship the consensus shape. No graft is needed. If they wildly diverge, Phase A was under-specified. Reframe and re-run rather than averaging the divergence.

## Phase F: Verify

Verify the synthesized artifact like any other output, per the **principle-prove-it-works-yr** skill. If verification finds a problem the arena missed, either Phase A was wrong (re-frame and re-run) or a candidate caught it and you missed the graft (go back to Phase E). Don't paper over it.

## Outputs

One synthesized artifact, with a short synthesis note alongside naming the base and why, the cross-judge's verdict, each graft with its source candidate, what was rejected and why, any convergence or dropouts, and the verification result.

# Graph (yr)

Two graphs exist. Keep them apart.

- **Live index**: `.codegraph/` in the repo, made by codegraph. Fast to query, not readable as a document, and ignored by git (a wildcard `.gitignore` inside it).
- **Snapshot**: `openspec/graph.md`, a readable file generated from the code. It is committed, so it travels with the proposal and the specs.

Modes: `sync`, `read`, `snapshot`. The caller says which one.

## Step 0. What is available

Check three things, once per session, and remember the answers:

1. **MCP tool.** Is a codegraph tool present, usually `codegraph_explore`? If tools are deferred, look for it with ToolSearch.
2. **CLI.** Run `codegraph --version`. Run `codegraph --help` once and trust it over the command names in this skill if they differ.
3. **Source files.** Does the repo have source code yet? A new project has none. Skip `sync` and `read` for it.

Write the result to `codegraph:` in the status file (`mcp`, `cli` or `none`; `mcp` if both exist) so later steps do not check again.

If neither the MCP tool nor the CLI exists, say so in one line, skip the codegraph steps and continue. `read` falls back to `openspec/graph.md` and **how-yr**. `snapshot` still works, because its script does not need codegraph.

Never run `codegraph install`. It edits the user's Claude settings and `CLAUDE.md`. Setup is the user's decision.

## sync

Run it at the start and at the end of any flow that touches code. The index does not update itself unless the codegraph MCP server watches this exact folder, and a freshly cloned repo may not be indexed at all.

1. `codegraph status`, run from the repo root with `(cd "<repo>" && codegraph status)`.
2. Not initialized: `codegraph init`, then `codegraph index` if `status` shows nothing indexed.
3. Initialized: `codegraph sync`.
4. If a command fails, show the error tail and continue without the graph. Do not retry in a loop.

## read

Understand an area before you change it. This replaces a broad exploration with **how-yr**.

1. Read `openspec/graph.md` if it exists. It is the cheap overview.
2. Ask the live graph about the area the task touches, in this order of preference: the MCP tool (`codegraph_explore` with a plain question about the symbol, file or behavior), then the CLI: `codegraph query <term>`, `codegraph node <symbol>`, `codegraph callers <symbol>`, `codegraph callees <symbol>`, `codegraph impact <symbol>`, `codegraph affected <files>` (the tests that cover a change), `codegraph context <task>`.
3. Read the files the graph points to. The graph says where to look. The code says what it does.
4. Give the user a short map, at most 30 lines: the modules involved, the entry points, who calls what, the tests that cover it, and anything surprising. Name the files and symbols.
5. Use **how-yr** only for what the graph cannot show: runtime behavior, data flow through many steps, or an area the index does not cover. Use **why-yr** only when the reason behind the code matters.

## snapshot

Regenerate `openspec/graph.md`. Run it near the end of every flow that changed code, after the review and before the archive.

1. Run the script. It reads the tracked Python files with `ast` and writes the file. It is deterministic: no dates, no hashes, sorted output.
   `"<venv-python>" "<this skill's folder>/scripts/graph_snapshot.py" --repo "<repo>" --out openspec/graph.md`
   Exit code 0 means written, 3 means nothing changed, 1 means an error.
2. If codegraph is available, refresh the notes block. Ask it for the structure that the script cannot show, such as the central symbols, the main call chains, and the cross-module links. Write at most 20 short lines in English between `<!-- codegraph:begin -->` and `<!-- codegraph:end -->`. Replace what was there. The script keeps this block on later runs.

#!/usr/bin/env python3
"""Write a readable, deterministic snapshot of a Python repo's structure. Standard library only.

  python graph_snapshot.py --repo <repo-root> [--out openspec/graph.md] [--max-lines 300]

What it reads: the files git tracks (or would track), `*.py` only. It parses them with
`ast`. It never imports or runs the code.
What it writes: module summaries, public classes and functions, and the internal import
graph as a mermaid diagram. No timestamps and no commit hashes, so an unchanged repo
gives a byte-identical file.

Text between `<!-- codegraph:begin -->` and `<!-- codegraph:end -->` in the output file
is kept as it is. graph-yr puts the codegraph notes there.
Exit code 0 = written, 3 = nothing changed, 1 = error.
"""
import argparse
import ast
import re
import subprocess
import sys
from collections import Counter, defaultdict
from pathlib import Path, PurePosixPath

BEGIN, END = "<!-- codegraph:begin -->", "<!-- codegraph:end -->"
SKIP_DIRS = {"openspec", ".venv", "venv", "node_modules", "build", "dist", "__pycache__"}


def git_files(repo):
    out = subprocess.run(
        ["git", "-C", str(repo), "ls-files", "--cached", "--others", "--exclude-standard"],
        capture_output=True, text=True, encoding="utf-8")
    if out.returncode != 0:
        raise SystemExit(f"git ls-files failed: {out.stderr.strip()}")
    return sorted({l.strip().replace("\\", "/") for l in out.stdout.splitlines() if l.strip()})


def is_test(rel):
    p = PurePosixPath(rel)
    return "tests" in p.parts or "test" in p.parts or p.name.startswith("test_") or p.name.endswith("_test.py")


def dotted(rel):
    parts = list(PurePosixPath(rel).with_suffix("").parts)
    if parts and parts[-1] == "__init__":
        parts.pop()
    return parts


def build_index(py_files):
    """suffix dotted name -> file, only when unique."""
    cand = defaultdict(set)
    for rel in py_files:
        parts = dotted(rel)
        for i in range(len(parts)):
            cand[".".join(parts[i:])].add(rel)
    return {k: next(iter(v)) for k, v in cand.items() if len(v) == 1 and k}


def resolve(rel, node, index):
    """Yield repo files imported by an import node."""
    names = []
    if isinstance(node, ast.Import):
        names = [a.name for a in node.names]
    elif isinstance(node, ast.ImportFrom):
        if node.level:
            base = dotted(rel)
            if not rel.endswith("__init__.py"):
                base = base[:-1]
            base = base[: len(base) - (node.level - 1)] if node.level > 1 else base
            mod = ".".join(base + (node.module.split(".") if node.module else []))
        else:
            mod = node.module or ""
        names = [mod] + [f"{mod}.{a.name}" if mod else a.name for a in node.names]
    for n in names:
        if n in index and index[n] != rel:
            yield index[n]


def summarize(path):
    src = path.read_text(encoding="utf-8", errors="replace")
    tree = ast.parse(src)
    doc = ast.get_docstring(tree) or ""
    doc = doc.strip().split("\n")[0][:100] if doc else ""
    classes, funcs = [], []
    for n in tree.body:
        if isinstance(n, ast.ClassDef) and not n.name.startswith("_"):
            methods = [m.name for m in n.body if isinstance(m, (ast.FunctionDef, ast.AsyncFunctionDef)) and not m.name.startswith("_")]
            classes.append((n.name, methods))
        elif isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef)) and not n.name.startswith("_"):
            funcs.append(("async " if isinstance(n, ast.AsyncFunctionDef) else "") + n.name)
    return tree, doc, classes, funcs


def node_id(label):
    return "n_" + re.sub(r"[^A-Za-z0-9]", "_", label)


def group_of(rel, depth):
    parts = PurePosixPath(rel).parts[:-1]
    return "/".join(parts[:depth]) if parts else "(root)"


def build(repo, max_lines):
    files = git_files(repo)
    py = [f for f in files if f.endswith(".py") and not (set(PurePosixPath(f).parts) & SKIP_DIRS)]
    src_py = [f for f in py if not is_test(f)]
    tests = [f for f in py if is_test(f)]
    index = build_index(py)
    errors, info, edges = [], {}, defaultdict(set)
    for rel in py:
        try:
            tree, doc, classes, funcs = summarize(Path(repo) / rel)
        except (SyntaxError, ValueError) as e:
            errors.append(f"{rel}: {type(e).__name__}")
            continue
        info[rel] = (doc, classes, funcs)
        for node in ast.walk(tree):
            if isinstance(node, (ast.Import, ast.ImportFrom)):
                for tgt in resolve(rel, node, index):
                    if tgt != rel:
                        edges[rel].add(tgt)
    other = Counter(PurePosixPath(f).suffix or "(none)" for f in files if not f.endswith(".py") and not f.startswith("openspec/"))
    fan_in = Counter(t for s in edges for t in edges[s] if s in info and t in info)

    out = [
        "# Code graph",
        "",
        "Generated by graph-yr. Do not edit by hand. Regenerate with `graph_snapshot.py`.",
        "This file is a reading aid for people and for Claude. The live graph is in `.codegraph/` (not committed).",
        "",
        f"Python files: {len(src_py)} source, {len(tests)} test. "
        + ("Other files: " + ", ".join(f"{n} {e}" for e, n in sorted(other.items())) + "." if other else "No other tracked files."),
    ]
    if errors:
        out += ["", "Could not parse: " + ", ".join(sorted(errors))]
    out += ["", "## Modules", "", "| File | Summary | Public symbols | Imports | Imported by |", "|---|---|---|---|---|"]
    rows = []
    for rel in sorted(f for f in src_py if f in info):
        doc, classes, funcs = info[rel]
        syms = [c + (f"({', '.join(m[:4])}{', ...' if len(m) > 4 else ''})" if m else "") for c, m in classes] + funcs
        shown = ", ".join(syms[:8]) + (f", +{len(syms) - 8} more" if len(syms) > 8 else "")
        n_out = len([t for t in edges.get(rel, ()) if t in info])
        rows.append(f"| `{rel}` | {doc.replace('|', '/')} | {shown.replace('|', '/')} | {n_out} | {fan_in.get(rel, 0)} |")
    out += rows
    if tests:
        out += ["", "## Tests", ""] + [f"- `{d}`: {n} file(s)" for d, n in sorted(Counter(group_of(t, 3) for t in tests).items())]

    for depth in (3, 2, 1):
        g = defaultdict(int)
        for s in edges:
            if s in info and not is_test(s):
                for t in edges[s]:
                    if t in info and not is_test(t):
                        a, b = group_of(s, depth), group_of(t, depth)
                        if a != b:
                            g[(a, b)] += 1
        nodes = {x for k in g for x in k}
        if len(nodes) <= 40:
            break
    out += ["", "## Dependencies", "", f"Arrows point from the importer to the imported package. Grouped by the first {depth} folder level(s); numbers count import edges between files.", ""]
    if g:
        out += ["```mermaid", "flowchart LR"]
        for n in sorted(nodes):
            out.append(f'  {node_id(n)}["{n}"]')
        for (a, b), n in sorted(g.items()):
            out.append(f"  {node_id(a)} -->|{n}| {node_id(b)}")
        out.append("```")
    else:
        out.append("No imports between folders.")
    hubs = [f"- `{f}`: imported by {n}" for f, n in sorted(fan_in.items(), key=lambda x: (-x[1], x[0])) if not is_test(f)][:10]
    if hubs:
        out += ["", "## Most imported files", ""] + hubs
    out += ["", "## Notes from codegraph", "", BEGIN, "(none)", END, ""]
    return out


def main(argv):
    ap = argparse.ArgumentParser()
    ap.add_argument("--repo", required=True)
    ap.add_argument("--out", default="openspec/graph.md")
    ap.add_argument("--max-lines", type=int, default=300)
    a = ap.parse_args(argv)
    repo = Path(a.repo)
    out_path = Path(a.out) if Path(a.out).is_absolute() else repo / a.out
    lines = build(repo, a.max_lines)
    old = out_path.read_text(encoding="utf-8").replace("\r\n", "\n") if out_path.exists() else ""
    m = re.search(re.escape(BEGIN) + r"\n(.*?)\n" + re.escape(END), old, re.S)
    if m:
        text = "\n".join(lines)
        text = text.replace(f"{BEGIN}\n(none)\n{END}", f"{BEGIN}\n{m.group(1)}\n{END}")
    else:
        text = "\n".join(lines)
    body = text.split("\n")
    if len(body) > a.max_lines:
        # keep the head and the notes block; drop module rows from the middle
        cut = len(body) - a.max_lines + 2
        start = next(i for i, l in enumerate(body) if l.startswith("| `")) + 1
        body = body[:start] + [f"| ... | {cut} more module row(s) left out to keep this file short. Use codegraph for the rest. | | | |"] + body[start + cut:]
        text = "\n".join(body)
    if text == old:
        print("unchanged")
        return 3
    out_path.parent.mkdir(parents=True, exist_ok=True)
    out_path.write_text(text, encoding="utf-8", newline="\n")
    print(f"wrote {out_path} ({len(text.splitlines())} lines)")
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))

name: grilling-yr
description: Grill the user relentlessly about a plan, decision, or idea. Use when the user wants to stress-test their thinking, or uses any 'grill' trigger phrases.
---

Interview the user relentlessly until you reach a shared understanding. Map this as a **design tree**: every decision branches into the decisions that hang off it.

Work the tree in **rounds**. The **frontier** is every decision whose prerequisites are already settled: the questions you can ask _now_ without guessing at answers you haven't heard yet. Ask the whole frontier in one round: number each question, give the user **options to choose from**, and give your **recommended solution**. Then wait for the user's answers before the next round.

Format a round like so:

```
❓ **Q1** - **<question title>**: <the question, with one to three sentences of context: what it decides and what depends on it>

- **A (recommended)** <option name>: <what it means in practice. Main benefit. Main cost.>
- **B** <option name>: <what it means in practice. Main benefit. Main cost.>
- **C** <option name>: <what it means in practice. Main benefit. Main cost.>
- **Other**: your own answer

➡️ I recommend **A**, because <one sentence tied to this user's situation>.

---

❓ **Q2** - ...
```

Rules for the options:

- **Two to four real options.** Each one is something a sensible person could choose. Do not pad with strawmen to make the recommendation look good. If only one answer is reasonable, give it as a proposed default and add the one alternative worth considering.
- **The recommendation comes first** and is marked `(recommended)`. It is a concrete solution, not "it depends". State the trade-off honestly: every option names its main cost.
- **Options differ in what they mean, not in wording.** Mutually exclusive unless you say "pick any".
- **Open questions get proposals.** When the answer is a name, a number, a date or a scope, propose a specific value and one or two alternatives. For "what is the goal?" style questions, offer the likely readings drawn from what you already know, and let the user correct them.
- **Facts you found, not asked.** If you already looked something up, say what you found inside the question and build the options on it.
- **Easy to accept.** Word each question so that "A", "yes" or "agree" accepts your recommendation. The user can also answer with a mix ("Q1 A, Q2 B, Q3 other: ...") or with free text.

Each round the user answers reshapes the tree: settled decisions push the frontier outward and unblock questions that depended on them. Recompute the frontier and ask the next round. A question whose answer depends on another question still open in this round belongs to a _later_ round, not this one. Start each later round with one line listing what is now settled.

Finding _facts_ is your job, never the user's. When a frontier question needs a fact from the environment (filesystem, tools, etc.), dispatch a sub-agent to find it; don't ask the user for anything you could look up yourself. Don't block on it: a running exploration is an unsettled prerequisite, so only the questions downstream of it wait for the sub-agent to report; ask the rest of the frontier now. The _decisions_ are the user's: put each to them and wait.

The session is done when the frontier is empty: every branch of the design tree visited, nothing left silently assumed. Do not act on it until the user confirms you have reached a shared understanding.

## Principles

Read the leaf skill in full for any principle you apply. Each entry names when it applies. Each leaf is the **principle-<title>-yr** skill, with the title in kebab case, hyphens kept and other punctuation dropped, unless the entry gives its name.

**Core**

- **Laziness Protocol.** Refactoring, sizing a diff, or tempted to add abstractions, layers, or signal threading. Bias to deletion and the smallest change that solves the problem.
- **Foundational Thinking.** Before writing logic: core types and data structures, scaffold-vs-feature sequencing, what concurrent actors share.
- **Redesign from First Principles.** Integrating a new requirement into an existing design. Redesign as if it had been foundational from day one.
- **Attack the Premise.** Two or more fixes that share one premise have failed the same gate. Write the premise down and test it directly before you write another fix that assumes it.
- **Subtract Before You Add.** Sequencing an addition, refactor, or rewrite. Remove dead weight first, then build on the simpler base.
- **Minimize Reader Load.** Reviewing or shaping code that's hard to trace. Count layers and hidden state, collapse one-caller wrappers, shrink mutable scope.
- **Outcome-Oriented Execution.** Planned rewrites and migrations with explicit phase boundaries. Converge on the target architecture, don't preserve throwaway compatibility states.
- **Experience First.** Product, UX, or feature-scope tradeoffs. Choose user delight over implementation convenience.
- **Exhaust the Design Space.** A novel interaction or architectural decision with no precedent. Build 2-3 competing prototypes and compare before committing.
- **Build the Lever.** Any non-trivial work. Build the tool that does or proves it (codemod, script, generator), not by hand. The tool is the artifact a reviewer reruns.

**Architecture**

- **Model the Domain.** Writing stateful logic, or code that branches a lot or repeats a shape assumption across files. Encode the domain in a structure (state machine, typed model, table or registry, reducer, boundary, the right collection) instead of scattered conditionals.
- **Boundary Discipline.** Wiring validation, error handling, or framework adapters. Guards at system boundaries, trust internal types, keep business logic pure.
- **Type System Discipline.** Designing types or a signature in any typed language. Make illegal states unrepresentable, brand primitives, parse external data at boundaries.
- **Make Operations Idempotent.** Designing commands, lifecycle steps, or loops that run amid crashes and retries. Converge to the same end state.
- **Migrate Callers Then Delete Legacy APIs.** Introducing a new internal API while old callers exist. Migrate and delete in one wave.
- **Separate Before Serializing Shared State.** Concurrent actors might write the same file, branch, key, or object. Eliminate the sharing first.

**Verification**

- **Prove It Works.** After a task, before declaring done. Verify against the real artifact, not a proxy or "it compiles".
- **Fix Root Causes.** Debugging. Trace each symptom back to the first place the system went wrong and fix it there. A guard is a fix only when the state it handles is legitimate.
- **Sequence Work into Verifiable Units** (**principle-sequence-verifiable-units-yr**). Multi-step work (sweeps, migrations, runs of similar edits) and how you stack commits and PRs. Break work into small units that each end in a check, verify each before the next, and order delivery so the sequence proves itself.
- **Test Behavior, Not Implementation.** Writing, changing, or keeping a test. Assert what the code's users can observe, so the test fails when that behavior breaks and keeps passing when only the internals change.
- **Explain the Number.** Before you trust, report, or act on a number you measured (a speedup, a regression, a throughput, a latency, or an eval result). Find what limits it, and rule out that it measured something other than the work you think.

**Delegation**

- **Guard the Context Window.** Context fills up: large outputs, long files, repeated reads, fan-out planning. Route bulk to subagents, keep summaries in the main thread.
- **Never Block on the Human.** Tempted to ask "should I do X?" on reversible work. Proceed, present the result, let the human course-correct.

**Meta**

- **Encode Lessons in Structure.** You catch yourself writing the same instruction a second time. Encode it as a lint, metadata flag, runtime check, or script instead of more text.

## Autonomy

**Just do it.** Reversible work and local actions proceed without asking.

**Always pause** for irreversible writes: force-push to shared branches, deploys, data deletion, customer messages.

**Session overrides:** "don't stop", "run until done" mean keep going.

**No is an acceptable answer.** Asked whether to do something, invited to add scope, or shown an approach, give your real judgment. Decline, push back, or say "this doesn't earn its place" when that is true. A recommendation is a judgment, not a validation. Candor beats agreement.

## Multi-agent mode (only when the user opted in)

- Spawn with `subagent_type: "poteto-agent-yr"` and `run_in_background: true`. Do not set `model`. Pass file pointers, not inlined context. Give the absolute path of this `SKILL.md`.
- Every file-writing delegate gets its own worktree (`isolation: "worktree"`) or an exclusive branch. Do not write files or run a suite in a worktree a delegate still holds. Fencing a file in the prompt is not a lock (**principle-separate-before-serializing-shared-state-yr**).
- Code-writing goes to a delegate with a specific scope: file paths, the named data shape and its organizing structure, and success criteria. Trivial mechanical edits can stay with you.
- When the implementation admits several valid shapes (error handling, abstraction layer, test structure), run **arena-yr** instead of a single delegate.
- Give new work to a fresh delegate with consolidated scope: the original brief, every later directive, and the prior agent's report and branch. Resume an existing delegate only when the work strictly needs state that lives in it (uncommitted changes, a running process).
- You own every delegate's work. Review the diff and write your own summary. Stop an abandoned delegate and confirm it stopped before you reuse its worktree.
- Write the throughput checkpoint as four todo items (Feature step 3). A dimension that does not apply keeps its item with `n/a: <reason>`.

## Writing the reply

- Reply in the user's language. Default to Traditional Chinese for conversation.
- Short declarative sentences. One thought each.
- Every claim carries its evidence or its label in the same sentence: measured, inferred, or guess. A prediction or an unseen cause is a guess. Never hand the user a check you could run.
- Never fabricate a link, citation or transcript reference. Link only what you produced or read this session.
- Frame impact for the consumer and the maintainer: who the work is for, what changes for them, and what the next engineer who owns this code inherits.
- Terse is not an excuse to drop content. Every item a playbook's reply names stays.

## Comments

Write comments clean as you go. Keep a comment only for a non-obvious *why* that the code cannot show. A verify or test script gets no phase-narrating comments. The assertion or log string documents the step. This applies to every file you produce, including a delegate's diff.

### Bug fix

**You own this task. Plan, review, verify.** In single-agent mode (default) you investigate and fix it yourself. In multi-agent mode you delegate the investigation and the fix, and stay in the lead.

Be scientific. Every shipped line traces to runtime evidence. A belt-and-suspenders change that "might help" is a hypothesis, not a fix, and it does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

Start by getting the report straight: expected behavior, actual behavior, and the steps or input that trigger it. Ask the user only for what you cannot find yourself.

1. Reproduce it yourself on the matching surface (see Non-negotiables in poteto-mode-yr), even when a debug protocol says to ask the user to reproduce. Ask the user only with a stated, specific reason that you cannot reach the target, and only after driving it as far as it goes. If it will not reproduce, synthesize the trigger, tighten conditions, or instrument until it fires.
2. Binary-search the cause. Form candidate hypotheses, then rule them out until one survives. Seed them with the graph read the flow already did (callers, callees, the tests that cover the area), **how-yr** for runtime behavior the graph cannot show, and **why-yr** for regression history. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, and eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Do not guess. Confirm the surviving mechanism with runtime evidence before you plan the fix. If two fixes that share one premise fail the same gate, apply **principle-attack-the-premise-yr**.
3. **Approval stop.** This is the one place the workflow deliberately blocks on the human, as an exception to **principle-never-block-on-the-human-yr**, because the user wants to approve every fix. Do not change any code yet. Show the user, in Traditional Chinese: the root cause with its runtime evidence, the proposed fix (files, the change in a few lines, why it fixes the cause and not the symptom), the risk and the blast radius, and how you will verify. Ask with `AskUserQuestion`: Approve / Revise the fix / Stop. Record the approved root cause and fix as a line in the status file. Only after "Approve" go on.
4. Plan the fix. If it crosses a function or module boundary, run **architect-yr** in `design-only` mode first, and show the user the result as part of the approval. Then fix it:
   - **Single-agent (default).** Make the fix yourself, at the root cause (**principle-fix-root-causes-yr**).
   - **Multi-agent on.** Delegate the fix to `poteto-agent-yr` with a specific scope.
   - If the fix needs more than you approved, stop and ask again.
5. Verify on the same surface. The original repro now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence.
6. Stage the commits so the failing repro lands before the fix in git history. Use **tdd-yr** in bug-fix mode when TDD is on or the bug has a cheap local test path. Skip it when the test would be expensive, integration-heavy or unclear. This is the canonical case for **principle-sequence-verifiable-units-yr**: the failing test first, the fix on top.
7. Clean up the diff against `dev`: run **deslop-yr**, then **no-comments-yr**, and commit the result on its own. Then stop. The flow continues with review. Do not push and do not merge.

**Reply:** what was broken, the root cause, the fix, how you verified. Quote the decisive failing and passing output, trimmed to the assertion and the counts.

### Landing

Run by the entry flow (**yr-coding-skills**) after the review and the archive. It puts the work branch on `dev`. It never touches the default branch (`master` or `main`). `dev` is not protected, and the user opens the pull request from `dev` to the default branch by hand in their repo host.

This version does not watch CI and does not answer review comments.

## Before landing

1. `git -C "<repo>" status --porcelain` must be empty. If it is not, show the files and stop.
2. Run the test command from the status file once more. If it fails, stop. Do not land a red branch.
3. The commits are clean and ordered (**principle-sequence-verifiable-units-yr**), each landable on its own. **deslop-yr** and **no-comments-yr** should already have run at the end of the playbook. If the log or the diff shows they did not, run them now, before anything else. If the branch has messy history, use `git reset --soft <merge-base>` and recommit in slices, since interactive rebase is not available. Do this only on a branch that has not been pushed.
4. Commit messages are English, Conventional Commits `type(scope): subject`, no trailing period. Types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`. The subject is short, imperative, and names a real symbol when one carries the change. Bodies do not restate the subject. Write them with **technical-writing-yr**, then **unslop-yr**.

## Update from `dev`

Run `git -C "<repo>" fetch origin`. If `origin/dev` has new commits, run `git -C "<repo>" rebase origin/dev` on the work branch. On a conflict, stop and show the files. After a rebase, run the tests again.

If the conflict is only in `openspec/specs/<domain>/spec.md` (someone else changed the same spec on `dev` while you worked), the archive step can be replayed. Tell the user first. Then, for each conflicted spec:

1. Take the `dev` side: during a rebase that is `git -C "<repo>" checkout --ours -- openspec/specs/<domain>/spec.md`.
2. Re-apply the change's delta with the script of **archive-yr**: `"<python>" "<archive-yr folder>/scripts/openspec_archive.py" remerge openspec/changes/archive/<date>-<name> --specs openspec/specs`. It stops with an error if a MODIFIED or REMOVED requirement no longer exists on `dev`. Then the user must decide by hand.
3. Show the user the diff of the spec, because a MODIFIED requirement overwrites the `dev` version of that requirement.
4. `git add` the spec, then `git rebase --continue`.

Any other conflict (code, tests, `graph.md`): `graph.md` is generated, so take either side and regenerate it with **graph-yr** `snapshot`. Code and test conflicts are the user's to resolve.

## Ask how to land

Ask with `AskUserQuestion`:

- **Merge into dev and push (recommended).** `git switch dev`, `git pull --ff-only`, `git merge --no-ff <branch>` with the message `merge: <name>` and a one-line summary, run the tests, `git push origin dev`. Then offer to delete the local work branch. Never delete a remote branch without being asked.
- **Push the branch only.** `git push -u origin <branch>`. The user merges it themselves.
- **Leave it local.** Do nothing more.

A push of `dev` is the user's shared branch. The question above is the confirmation. Never force-push.

## Promotion to the default branch

Do not do it. When the user wants to promote, offer to write the pull request text for `dev` to the default branch, and print it in the reply. The user pastes it into their repo host. If the remote is on GitHub and `gh` works, you may run `gh pr create` only when the user asks for it.

The text is a one-minute briefing for a reviewer. Titles use Conventional Commits. Use `##` headings in this order, and drop a section with nothing to say:

- `## Why`: the problem and approach, one to three short sentences.
- `## What changed`: one to three short bullets. Name a real symbol or path only when it carries the change.
- `## Scope`: always. What it covers and what it leaves out. Link the proposal in `openspec/changes/archive/`.
- `## Tradeoffs`: only rejected alternatives a reviewer would otherwise ask about.
- `## Blast Radius`: one or two sentences on who or what it touches, and why that is safe or risky.
- `## Verification`: one to three bullets, each a real run path and its outcome. Link `openspec/reviews/<name>.md`.

Full SHAs, file-by-file checklists and long logs go in a linked file, not the body. Prefer several narrow pull requests to one large one.

**Reply:** where the work landed (branch, commit, pushed or not), the test result, and whether the user needs to open the pull request to the default branch.

**You own the contract. The structure changes. The behavior does not.** Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

0. **Behavior contract.** List what must not change, as B1, B2, ...: the public functions and their callers (`codegraph callers`, `impact` through **graph-yr**), the scenarios of the specs that touch the area, and the tests that cover it (`codegraph affected`). 4. Subtract before you add. 5. Move in small behavior-preserving steps, each keeping the pin green. # Attack the Premise

When two or more fixes that share one premise have failed the same gate, suspect the premise, not the fixes.

**Why:** Each failed fix is evidence against the belief it assumed. A third fix on the same premise spends effort where the evidence already says the cause is not.

**Pattern:**
- **Write the premise down.** The premise is the one sentence that every failed fix assumed.
- **Test the premise before the next fix.** Find an observation that would come out differently if the premise were false, and make it. Look at how the failures are distributed, not only at how large they are. Make the check rerunnable per [Build the Lever](../principle-build-the-lever-yr/SKILL.md).
- **Follow the evidence.** If it contradicts the premise, the cause is elsewhere. Look for what the failures have in common that the premise did not predict. If it confirms the premise, ask the next "why" per [Fix Root Causes](../principle-fix-root-causes-yr/SKILL.md). The earlier fixes may have treated a consequence instead of the cause.
- **Remove the condition instead of compensating for it**, per the [Laziness Protocol](../principle-laziness-protocol-yr/SKILL.md). If the evidence shows that one part always lands on the losing side, change what puts it there. A mechanism that cleans up after it leaves the cause in place and adds work on every run.

**Stop:** Do not start the next fix before the premise is written down and tested.

This principle is distinct from [Redesign from First Principles](../principle-redesign-from-first-principles-yr/SKILL.md), which rebuilds a design around a new requirement. It questions a fact the current design assumes.

# Boundary Discipline

Place validation, type narrowing, and error handling at system boundaries. Trust internal code unconditionally. Business logic lives in pure functions. The shell is thin and mechanical.

**Why:** Scattered validation is noisy, redundant, and gives a false sense of safety. Keep logic out of framework wiring so it can be tested without the framework.

**The pattern:**
- **At boundaries** (CLI args, config files, external APIs, network protocols): validate, return errors, handle defensively.
- **Inside the system:** typed data, error propagation, no re-validation. Trust the types.
- **Across the boundary.** Expose domain concepts, not the boundary's private representation. Keep general-purpose mechanism inside and special-purpose policy at the edge.

**Applications:**

Validation and error handling:
- Validate config at parse time (the boundary), not inside business logic
- Parse raw data into domain types at the boundary
- Do not re-export transport, storage, framework, or wire types through the public surface
- No redundant nil checks deep in call chains if the boundary already validated

Code organization:
- Business logic in pure functions with no framework dependencies
- Parse functions: pure transforms from raw bytes to typed state
- Prompt construction: structured state in, string out
- Scoring and assessment: pure transforms from state to results

**The tests:**
- "Is this data crossing a system boundary right now?" If not, validation is redundant.
- "Can this be a pure function that the shell just calls?" If yes, extract it.

# Build the Lever

When the work isn't trivial, build the tool that does it instead of doing it by hand.

A codemod, generator, or script does the work the same way every time and reruns for free. The tool is one artifact a reviewer can read and rerun to check the work. Hand-done changes can only be re-verified by redoing them. A deterministic script turns "trust me" into "run this".

Default to building the lever. Skip it only when the task is trivial, a couple of obvious edits you can see at a glance.

- Do the first unit by hand to learn the recipe, then build the tool. Prove it by rerunning it on that unit and diffing against your hand-done version. Make the lever safe to rerun.
- For a comparison tool, seed one known-bad change for each output it claims to compare, and confirm the tool reports each mismatch. For example, change a total, then separately swap item assignments while keeping the totals. If required input is missing, the tool must refuse or report the result as inconclusive, never as a match. Keep these controls with the experiment and rerun them before you trust its results.
- Codemod or script for edits, generator for repetitive files, a dump-to-sqlite query for analysis, a rerunnable check for verification.
- A deterministic lever beats fan-out. If the tool can process every unit in one pass, run it yourself. Don't fan out delegates to hand-apply what a script can do.
- When you fan work out to subagents, write the lever as a skill they all read: the recipe, the verification contract, and the do-not-touch fences in one artifact. Keep it outside the delegates' write scope so they can't quietly edit the contract.
- Applying this principle produces a file. If you cited it and there is no codemod, script, generator, or delegate skill in the diff, you didn't apply it.
- Commit the lever when the work outlives the session.

The bar is triviality, not repetition. A one-off still earns a lever when the lever is what makes the work checkable. Per the [Laziness Protocol](../principle-laziness-protocol-yr/SKILL.md), build the smallest script that does or proves the job, never a framework.

Distinct from [Encode Lessons in Structure](../principle-encode-lessons-in-structure-yr/SKILL.md), which makes a recurring instruction a durable guardrail. This is throughput and reviewability on the work in front of you. For scripting the verification itself, see [Prove It Works](../principle-prove-it-works-yr/SKILL.md).

# Make Operations Idempotent

Design operations so they converge to the correct state regardless of how many times they run or where the previous run stopped. Every state-mutating operation should answer: "What happens if this runs twice? What happens if the previous run crashed halfway?"

**Why:** Commands, lifecycle operations, and processing loops run where crashes, restarts, and retries are normal. If partial state changes the next run's outcome, every restart becomes a debugging session.

**The idea:** derive each step from the state that exists, not from what the previous run meant to do. Read the current state, compare it to the goal, and apply only the difference. A step written this way is safe to repeat, because a repeat finds nothing left to do.

Anything a run leaves behind, such as a lock, a temporary file, a half-written record, or a claimed job, must be recognizable as stale by the next run. Judge staleness by evidence that stays true wherever the previous run could have stopped, not only in the common case. A marker that the next run cannot judge turns every crash into manual cleanup. For example, write to a temporary path and rename it into place, or compare artifacts by content instead of by creation order.

**The test:**
1. What happens if this runs twice in a row?
2. What happens if the previous run crashed at every possible point?
3. Does re-execution converge to the same end state?

If any answer is "it depends on what state was left behind," the operation needs a reconciliation step.

# Minimize Reader Load

Maintainability is the work a reader must do to understand code. - **Name the invariant at the boundary,** not in every consumer, so the reader learns it once.

# Prove It Works

Verify every task output by checking the real thing directly. Do not infer from proxies, self-reports, or "it compiles."

**Why:** Unverified work has unknown correctness. Indirect verification (file mtimes, output freshness, agent self-reports, cached screenshots) feels cheaper than direct observation. Acting on a wrong inference costs far more than checking the source.

- Read the actual value, not a cached or derived representation
- When verification fails, suspect the observation method before suspecting the system
- Before you report success (merged, sent, started), read the real state and the exit code. Truncated output (`| tail -1`) and your own echo prove nothing

Red is a colour, not a measurement. A failing check proves the instrument only when the failure content is the disagreement you predicted. A convergence probe keys on behavior only the new artifact can produce, never an identity field the old one also emits. A same-SHA restart lets old code report the new commit SHA.

The strongest proof is a deterministic script that re-runs the same comparison, not a one-time eyeball. Write the script, run it, and keep its output as an artifact a reviewer can re-run instead of trusting your word.

Keep the artifact visible for the human. Commit it only for large or complex work where the trail has to be auditable later, like a big port or migration. Otherwise keep it local.

# Test Behavior, Not Implementation

A test is a claim about what the code does for its users: a caller, an end user, or another service. Behavior is what those users can observe through the interface they use. That includes return values, errors, state they can read back, and effects on systems outside the code, such as a request sent, a row written, or a message emitted. Implementation is what they cannot observe: private helpers, internal call order, intermediate data, and which internal collaborator did the work.

Judge each test against two imagined edits:

- **Break the behavior.** Make the code return a wrong value, skip an effect, or do the effect twice. If the test still passes, it proves nothing. The usual causes are an assertion looser than the contract, an expected value computed by the code under test, a restated constant or prompt string that never runs the code that reads it, and an assertion on data that the test built itself.
- **Change the internals.** Keep every observable result the same and restructure the code underneath. If the test now fails, it is pinned to the implementation. It will need a rewrite on every refactor and still catches no bug.

Keep a test that catches the first edit and survives the second. Rewrite or delete the rest. To write a test that does both, drive the code through its users' interface with a concrete input. Derive the expected value from the requirement, not from a run of the code. Assert what the contract promises, no less and no more.

The contract decides, not the shape of the assertion. When "an empty cart never charges" is the promise, an assertion that the payment client got no call is behavior. Pair it with a case where the charge happens, so that the test shows it can see a call. The payload that a mocked external service receives is behavior, because that service observes it. A call to an internal helper is implementation, because no user can see it. An empty list is the exact answer when no record matches, and a hollow check when the test only needs some result. An exact error message pins wording that no caller reads. The error type that callers branch on is the contract.

A test can pin an invariant instead of a call, such as a key that must exist in two tables or a compile-time type check. The invariant is the behavior. A constant pin is behavior when the value is a promise to users, such as a documented default, so name that promise.

- `<name>`: the change name in kebab case, already decided by the entry skill.

## Step 3. The interview

These rules keep the interview about requirements and not about solutions.

1. **Need before solution.** When the user names a solution ("use Redis", "add a queue"), ask what need it serves. Record the solution as a constraint only when it is a real one, such as an existing system or a company rule.
2. **Every requirement is testable.** A requirement is one sentence with SHALL or MUST. It has one or more scenarios in GIVEN / WHEN / THEN form. A requirement with no scenario is not finished.
3. **Ask for out-of-scope items.** Ask what is not part of this change. Write it down in the proposal.
4. **Chase vague words.** "Fast", "simple", "secure", "scalable", "later": ask for a number, an example or a date.
5. **Walk edge cases.** Empty input, failure halfway, two users at once, a huge input. Each answer becomes a scenario or an out-of-scope line.
6. **No design here.** Types, modules and code shape belong to **architect-yr**. Technical constraints (language, platform, existing systems, company rules) go in the proposal under Scope.

**Names matter.** A requirement name is unique in its domain. A scenario name is unique in the change, and its test is `test_<scenario name in snake_case>`. Names are used to match MODIFIED and REMOVED later, so pick them once and keep them.

### `greenfield` mode

Run the full interview until the frontier of the design tree is empty. Cover: the goal and who it is for, the capabilities (each becomes a domain, usually 1 to 5), each requirement with scenarios, out of scope, constraints (language, platform, deployment, company rules), and open questions. ### `feature` mode

The user has already stated the requirement. Keep it short: one or two rounds.

1. Restate the requirement in one or two sentences, and name the domain(s) it touches from `openspec/specs/`. A new capability gets a new domain.
2. Draft 2 to 5 scenarios yourself from the requirement, the existing spec and the graph. Include at least one edge or failure case.
3. Ask in one round: the scenarios (confirm, change, add), out of scope, and anything you could not find out from the code. Give your recommendation for each question.

If the feature changes an existing requirement, write it as MODIFIED with the whole requirement and all its scenarios. If it removes one, write REMOVED with a reason.

# TDD (yr)

Three modes. The caller names the mode: **bug-fix**, **feature**, or **refactor**. The numbered workflow below is bug-fix mode. Feature and refactor modes are at the end.

When fixing a bug with a clear, cheap test path, make the broken behavior executable before changing production code. The goal is a focused regression test that fails before the fix and passes after it.

Do not force a test when it would be impractical. If the available test would require broad harness setup, brittle mocks, slow end-to-end infrastructure, production-only state, vague reproduction steps, or large unrelated fixture churn, skip adding a new test and use the closest useful verification instead.

## Workflow (bug-fix mode)

1. **Understand the bug.** Identify the intended behavior, current behavior, affected path, and smallest observable reproduction.
2. **Choose the narrowest executable check.** Prefer the closest unit, component, integration, or regression test already used for that codepath. If no practical test path is obvious, do not create one from scratch just to satisfy the workflow.
3. **Write the failing test first.** Add the smallest focused test that would have caught the bug. The test should encode intended behavior, not mirror the current implementation.
4. **Run the new test before fixing.** Confirm it fails for the intended reason. Quote the failure content, not the assertion line: an exception, an empty result against a literal, and the predicted mismatch all print red, and only the last one proves the test measures the bug. If it passes or fails for an unrelated reason, correct the test or reproduction before editing the implementation.
5. **Fix the bug.** Make the smallest production change that satisfies the intended behavior while preserving nearby contracts.
6. **Rerun the regression test.** Confirm the test now passes.

## If a Failing Test Is Impractical

Use the closest executable regression check instead: a targeted script, manual reproduction command, browser automation, snapshot comparison, log assertion, or focused integration check.

Prefer no new test over a bad test. A bad test is one that mostly tests mocks, encodes current implementation details, depends on timing or unrelated global state, needs expensive infrastructure for a small fix, or would be deleted immediately after proving the fix.

## Guardrails

- Do not change tests merely to match a wrong implementation.
- Do not weaken existing assertions unless the expected behavior has genuinely changed and the reason is clear.
- Keep the regression test focused on the bug. Avoid broad fixture churn or unrelated coverage expansion.
- If the bug is flaky, make the test deterministic where possible and document the signal being locked down.
- If the bug exposes a broader class of failures, first land the focused regression path, then consider additional sibling coverage.

## Final Response

Report the evidence, not just the outcome:

- Name the failing-before test or executable check and quote the failure it produced, trimmed to the diff.
- Name the passing-after test run and any nearby validation performed.
- If failing-before evidence could not be demonstrated, state why and describe the closest regression check used instead.

## Feature mode

Red to green in vertical slices, one scenario at a time.

1. **Agree the seams once.** A seam is the public boundary you test at: the interface where you observe behavior without reaching inside. Before the first test, state the seams under test in one line each (what it catches, what it misses) and confirm them with the user if they are not obvious. Do not write tests at an unconfirmed seam. You cannot test everything, so effort goes to the critical paths and the complex logic.
2. **One slice at a time.** Take one scenario from the change's delta spec. Name the test `test_<scenario name in snake_case>`, so **archive-yr** can match it. If the skeleton already has that test as a skip, replace the skip. Write one failing test whose expected value comes from the scenario's THEN lines. Run it and confirm it fails for the intended reason. Write the smallest code that passes it. Run it green. Repeat for the next slice.
3. **Do not write all the tests first.** Bulk tests verify imagined behavior and commit you to a test structure before you understand the implementation. Each test is a tracer bullet that responds to what the last cycle taught you.
4. **Refactoring is not part of the loop.** It belongs to clean-up after green (**deslop-yr**, review), not to the red-green cycle.

Anti-patterns to avoid:

- **Implementation-coupled tests.** Mocking internal collaborators, testing private methods, or checking through a side channel. The tell: the test breaks when you refactor but behavior has not changed (**principle-test-behavior-not-implementation-yr**).
- **Tautological tests.** The assertion recomputes the expected value the way the code does, so it passes by construction. Expected values come from an independent source: a literal, a worked example, the requirement.

## Refactor mode

Characterization pins. The goal is a test that stays green while the structure moves.

1. Take the behavior contract (B1, B2, ...) from the status file (`## Behavior contract`). For each behavior, prefer an existing test. Where there is none, write a test at the public seam that records what the code does now.
2. **Run every pin on the current code and see it pass before you touch any structure.** A pin that fails on the current code is wrong, or it found a bug. If it found a bug, record it as separate work and pin the current behavior or exclude that case from the contract, with the user's agreement.
3. Assert observable behavior only. Do not pin internals, call counts or private helpers, because those are exactly what the refactor is going to change.
4. After every refactoring step, run the pins. A red pin means the step changed behavior. Fix or revert the step. Never edit a pin to match new behavior unless the user agrees the contract changed.
5. Do not add tests for new behavior in a refactor.

# Technical writing

Write so a tired engineer understands on the first read. Apply all four layers.

Three rules sit above the layers:

- **Cut every word that does no work.** If the sentence survives without a word, the word goes. "In order to" is "to". "It is important to note that" is nothing.
- **Use the short, everyday word.** "Use", not "utilize". "Help", not "facilitate". "Do", not "perform". A long word has to buy its length with precision.
- **When a rule makes a sentence worse, fix the sentence another way or leave it alone.** A sentence that follows every rule and sounds like a machine wrote it has failed.

The codebase is the word list. Write the real symbol, file, flag, or command name, not a synonym or a description of it.

Don't invent jargon. Use the words a developer would say out loud: "move", "delete", "a budget that only decreases", not "evacuate", "ratchet", or "endgame". A named pattern is fine when the doc says what it means the first time. Propose a new offender and its replacement as an addition to `unslop-yr`'s abstract-metaphor rule in your reply, with the diff. Don't edit that skill.

## Vary the rhythm

A doc can obey every layer and still read machine-written: every sentence clipped short, no view anywhere, nothing specific.

- Mix sentence lengths on purpose. Short sentences land a point. Longer ones carry a fact with its condition or consequence.
- One thought per sentence does not mean one length per sentence. Split the sentence that carries two thoughts. Keep the long sentence that carries one.
- Have a view where the mode allows it. Explanation weighs trade-offs, so say what you make of them instead of listing pros and cons. Reference stays dry.
- Be specific over sterile. Not "schema changes can cause issues" but "a column rename fails the build".

## Pick the mode first (Diátaxis)

One document, one mode. Two questions pick it: does the content inform action (doing) or understanding (thinking), and does it serve learning or work?

- Action + learning: **tutorial**.
- Action + work: **how-to**.
- Understanding + work: **reference**.
- Understanding + learning: **explanation**.

Use the compass on a whole document or on one sentence.

**Tutorial: learning by doing.** The learner's success is your job, not theirs. Open by saying what the learner will build, not what they will "learn". Every step produces a visible result, early and often. Tell them what they should see: the expected output, the prompt change, the log line. Cut explanation to one clause and a link. Stay concrete. Write as "we", in commands: "First, do x. Now, do y."

**How-to: steps to a goal.** Solve a problem a person has, not an operation the machine can perform. Assume competence and skip teaching. Action only: no digressions, no background, no completeness for its own sake. Link those instead. Allow forks and judgment: "If you want x, do y." Name the guide by the task: "How to calibrate the radar array", not "Radar array calibration".

**Reference: facts for lookup.** Only describe. No instruction, no persuasion, no opinion. Be dry, complete, and sure. State facts, options, limits, and errors with no hedging. Mirror the structure of the thing described, so code and docs can be navigated together. Put material where readers expect it. Generate from code where possible.

**Explanation: understanding and why.** One bounded topic, readable away from the product. Each title should tolerate an implicit "About..." in front. Anchor on a real why question. Give context: design decisions, history, constraints, alternatives. Opinion is allowed here and nowhere else.

Don't mix modes: no reference tables inside a tutorial, no tutorial hand-holding inside reference, no arguing inside a how-to. Split and link instead.

## Write sentences to the reader (Google developer style)

- Talk to the reader as "you", in the present tense. "Will" only for things that genuinely happen later.
- Say who does what: "the compiler checks", not "is checked". Passive is fine only when the actor is unknown or beside the point.
- Write instructions as commands: "Click Submit." State facts plainly. Never "should be done".
- Put the condition before the instruction: "To delete the document, click Delete."
- Put the common case first. Exceptions after.
- Sound like a knowledgeable friend. No buzzwords, no figurative language, no "please" in instructions, and never "simply", "easy", or "quickly" in a procedure. If it were simple, the reader would not be here.
- Don't pre-announce ("we will soon support...") and don't start consecutive sentences with the same phrase.
- Link with words that say where the link goes: the page title or a short description. Never "click here". Prefer a sentence of context on the page over a link off it.
- Headings carry the point, not just the topic ("Pick the mode first", not "Modes"). Sentence case. A task heading is a bare verb phrase ("Create an instance"). A concept heading is a noun phrase. One h1 per page, no skipped levels.
- Numbered lists for sequences, bullets for everything else. Introduce a list with a complete sentence. Keep items parallel.
- Code goes in code font. UI elements go in bold. Use serial commas. Drop "etc." and say up front that a list is partial.

## Make statements load one at a time (STE rules)

- One instruction per sentence. One thought per sentence everywhere else.
- Split instructions longer than about 20 words and other sentences longer than about 25.
- Put the warning or condition before the step it guards: "If hot oil touches your skin, injuries can occur."
- Keep "the" and "a": "Remove backup file" reads two ways. "Remove the backup file" reads one.
- Give each word one meaning and one job, then keep it. If "check" means inspect, don't also use it for restrain.
- Pick one word per action and stick to it: "start", not "start" here and "initiate" there.
- Write procedures as direct commands, never as narration and never in the passive: "Install the component", not "the component must be installed".
- Avoid "-ing" words where you can.

## Leave no sentence open to two readings (Global English)

- Keep words like "only" and "not" next to the word they change: "only fails on growth" and "fails only on growth" say different things.
- Break up long noun strings: "the proto import budget check script" becomes "the script that checks the proto-import budget".
- Make every "it", "they", and "this" point at one obvious thing. Repeat the noun when in doubt. Never use "this" or "which" to point at a whole clause.
- Don't drop verbs: "Phase 1 moves the converters and Phase 2 the runtime" leaves Phase 2 without one. Give it one.
- Keep the small words that show structure, such as "that" in "Ensure that the switch is off". Never trade clarity for word count.
- Repeat the article in a series when it prevents a misread: "the client and the host", not "the client and host", when they are two things.
- Say which parts "and" or "or" joins when a sentence can group two ways. "Both...and", "either...or", and "if...then" are free disambiguators.
- Use periods, not semicolons. Replace an em dash with a new sentence.
- Make text in parentheses a full grammatical unit or its own sentence. Never form plurals with "(s)".
- No slashes: write "a, b, or both" instead of "a/b" or "and/or".
- Call each thing by one name, everywhere. A doc that says "the gate", "the ratchet", and "the budget check" for one thing teaches three things. Don't churn what didn't change.
- Skip idioms, colloquialisms, Latin abbreviations, and metaphors.

## Voice and repo specifics

- Apply the **unslop-yr** skill to every doc this skill touches. That skill owns the slop-pattern catalog: AI vocabulary, filler, hedging, formatting tells.
- PR descriptions and commit messages are writing too. Every layer except Diátaxis applies to them. A PR body is a briefing that a reviewer can read in under a minute. Do not paste long logs, SHA lists, or metric tables. Link them.
- Product UI strings are not documentation. Use your product's copy guidelines for those.
- Indent code snippets with tabs. Write real paths. Make every count or tree claim true at the commit that lands it, and include the command that regenerates it.

## Worked example

Before:

> Configuration of the proto import ratchet budget script parameters is performed via budget.json. Note that it's important to remember that running with --write, which updates the committed budget to reflect the current count, should only be done when lowering it. If exceeded, CI fails.

After:

> `budget.mjs` reads the committed budget from `budget.json` and counts the files that import protos. If the count exceeds the budget, CI fails. Run `budget.mjs --write` only to lower the budget.

# Unslop

Edit text to remove AI patterns. Scan for the patterns below, then rewrite. Preserve meaning and match the intended tone.

## Patterns to detect and fix

Rule numbers are stable ids that other skills cite. A removed rule leaves a gap.

### Content

3. **Superficial -ing phrases.** "highlighting...", "ensuring...", "reflecting...", "showcasing...", "fostering...". Delete or expand with real sources.
5. **Vague attributions.** "Experts believe", "Industry reports suggest", "Some critics argue". Name the source or delete.

### Language

7. **AI vocabulary.** Additionally, crucial, delve, enduring, enhance, fostering, garner, interplay, intricate, landscape (abstract), pivotal, showcase, tapestry (abstract), testament, underscore, vibrant. Replace with plain words.
8. **Fancy ways to say "is".** "serves as", "stands as", "boasts", "features". Say "is" or "has".
9. **"Not just X, but Y."** State the point directly instead.
10. **Rule of three.** Don't force ideas into groups of three. Use the natural number.
11. **Synonym cycling.** Protagonist, main character, central figure, hero all in one paragraph. Pick one, repeat it.
12. **False ranges.** "from X to Y" where X and Y aren't on a meaningful scale. List topics directly.

### Style

13. **Em dash overuse.** Avoid em dashes entirely. Use periods or commas only (no parentheses, no en dashes, no hyphen-as-dash substitutes). If a thought needs separation, end the sentence or use a comma.
14. **Colon overuse.** Colons are fine before a list or example, not as mid-sentence connectors. "If you're coming from traditional automation: instead of registering event handlers, you describe conditions" adds nothing with the colon. Rewrite to let the point stand on its own without comparison framing. "Describing when the scheduler should fire works best as plain English." Same meaning, no crutch punctuation.
15. **Boldface overuse.** Don't bold every proper noun or acronym.
16. **Inline-header lists.** The tell is a bold label and colon that restates the line: "**Performance:** Performance improved...". Convert those to prose. A bold lead-in that ends in a period, names the item, and is followed by genuinely new detail ("**Schema in TypeScript.** Tables live in one file.") is fine, not a tell.
17. **Title case headings.** Use sentence case.
18. **Decorative emojis.** Remove from headings and bullets.
19. **Curly quotes.** Use straight quotes.

### Communication artifacts

20. **Chatbot phrases.** "I hope this helps!", "Let me know if...", "Of course!", "Certainly!", "Found the smoking gun!" Remove.
22. **Sycophantic tone.** "Great question! You're absolutely right!" Respond directly.

### Filler

23. **Filler phrases.** "In order to" becomes "To". "Due to the fact that" becomes "Because". Delete "It is important to note that".
24. **Excessive hedging.** "could potentially possibly be argued that it might" becomes "may".
25. **Generic conclusions.** "The future looks bright." State specific plans or facts.

### Jargon

26. **Abstract metaphor nouns.** Substrate (base), wedge, wedge in (add), vector (way, method), locus, vantage, nexus, primitive as a noun, harness as a metaphor, surface as in "API surface", bedrock, scaffolding as a metaphor, modality, paradigm, gold-plating (more than the job needs), ratchet as a metaphor (the mechanism's real name, or a limit that only tightens), evacuate for moving code (move out), endgame (the last phase), north star, flywheel. These read as technical but usually have a plainer concrete word. Pick the concrete word.

### Plain speech

27. **Say what it does, not how it feels.** "the database stays close at hand", "SQL you can read", "types that follow your schema" name a feeling. The fix names the mechanism or a number: "`.toSQL()` returns the exact string sent to the database", "a column rename fails the build". Ask what the sentence tells the reader to do or know, then write that. If you can't restate it as a concrete instruction, fact, or number, cut it. One more check: if the sentence could appear unchanged in another project's docs, it says nothing about this one. Cut it.
28. **Shorten or split dense sentences.** If the reader has to backtrack to parse a sentence, break it in two or drop clauses. One idea per sentence.
29. **Active voice.** Prefer it. Catch "is/are/was/were + past participle" and name the actor: "queries are validated" becomes "the compiler validates queries", "the file is parsed by the loader" becomes "the loader parses the file". Passive is fine only when the actor is unknown or genuinely doesn't matter.
30. **Cut adverbs, or use a stronger verb.** "runs quickly" becomes "is fast" or the number, and "significantly improves" becomes the measured delta. An adverb propping up a weak verb means the verb is wrong.
31. **Prefer the plain word.** "utilize" and "leverage" become "use", "facilitate" becomes "help", "numerous" becomes "many", "in the event that" becomes "if". The fancier synonym is rarely clearer.
32. **Mannered prose.** Metaphor or flourish where a literal phrase exists: aphorisms ("wire it or delete it"), rhetorical fragments for effect, personified code ("the plan holds it"), figurative verbs ("rides along", "stands on"), stock framing phrases. "A dial worth turning" becomes "a parameter worth varying". Say what you mean. Rule 26 covers the metaphor nouns.
33. **Over-compression.** Dropped articles, verbless fragments, symbol-speak, and abbreviations that make the reader decode instead of read. "Parser rejects bad date → exit 2, no write" becomes "The parser rejects a bad date, exits with code 2, and writes nothing." Write whole sentences with their articles and verbs, and spell out arrows and abbreviations.

# Why

Investigate the motivation and intent behind code. The companion `how-yr` skill answers what the code does and how it works. `why-yr` answers what forces led to its shape.

Do not set `model` on any spawn: subagents inherit the session model.

Every spawn is `general-purpose` with `readonly: false` (agent mode). **Do not use readonly/Ask mode.** It strips MCP access, which disables the MCP-backed investigators and the synthesizer's citation spot-checks. Investigators still shouldn't write anything.

## Operating Posture

Operate as a **careful, cautious, and precise investigator**. Be honest about what you know vs what you're inferring. Read `references/epistemics.md` for the full confidence framework and phrasing guide. The synthesizer must follow it.

## Step 1. Understand the Target and the Question

The **target** is usually a chunk of code, a pattern, a feature, or a named design decision. The **question** is usually a design rationale, a tradeoff, a motivating edge case, an external constraint, dead code, or a broad history sweep.

If the target is vague ("why do we do it this way?" with no clear referent), make your best guess from conversation context (open files, recent edits, cursor location, what was just discussed). State your interpretation briefly so the user can redirect if you're off, then proceed.

## Step 2. Establish the Code Anchor

Before spawning investigators, build the seed context inline: file paths and line ranges, key symbols (functions, classes, constants), the last few commits touching the target, PR numbers from merge commits (pattern `(#1234)` in the subject line), and any linked ticket IDs. Run `git blame -L <start>,<end> <file>` for last-touch commits, `git log --follow -p -- <file>` for full history with patches through renames, `git log --oneline -20 -- <file>` for recent commits with PR numbers visible, and `git log -1 --format=%B <commit>` to extract PR numbers. If the remote is not GitHub (for example Azure DevOps) or `gh` is not installed, skip the PR lookups: rely on `git log`, `git blame` and the commit messages, and record in the coverage map that PR discussion was not searched. Otherwise pull the PR bodies and discussion for any substantive commit: `gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews`. This anchor goes to every investigator and to the synthesizer.

### Discovery

# Epistemics

How to reason about confidence when evidence is historical, fragmentary, and sometimes contradictory, and how to tell the user without flattening it into false certainty. Code shows what it does, not *why it exists*. The why lives in commits, PRs, tickets, docs, and conversations, all incomplete, biased, and sometimes missing. Pretending otherwise produces confident-sounding guesses that mislead the user.

## Claims about human decisions

Before investigating whether a rule permits an action, identify the component or stage that owns the action and whether the question affects the current task. Ownership elsewhere may make the question unnecessary; it does not end a relevant cross-component investigation.

When the exact scope of a human ruling matters, locate the person's original attributable words. Preserve a source pointer, the speaker, and enough original wording to establish scope. Label an agent summary or interpretation as such, regardless of its age. A paraphrase alone cannot establish the original instruction's exact scope. If the original is unavailable, say so and leave that scope uncertain; do not invent a firm restriction or permission.

For example, "avoid that endpoint during this migration" and an agent's "the user permanently forbids that endpoint" are different claims. Report the scoped original and the broader interpretation separately. Copies of that interpretation in several notes form one dependent evidence chain, not independent decisions. Trace them to their source before increasing confidence. This rule concerns human rulings; ordinary factual reporting does not require verbatim quotes for every claim.

## Confidence Tiers

Every claim in the output must sit in one tier. The tier sets its section and its phrasing.

### 1. Direct

An explicit, textual citation answers the question: something an author actually *wrote* that says why, not "the code does X so the author must have wanted X." For example, a PR description "this fixes the bug where users with >1000 items couldn't paginate", a ticket "we're adding this because customer Acme requested it in their security review", a code comment "// clamp to 100 because the upstream API rejects larger values", a design doc "we chose option A over option B because we need persistence across restarts", or a chat message from the author "switching to this approach since the old one was flaky in tests".

Phrasing: confident, present tense, cited. "This exists because X."

### 2. Supported

Multiple pieces of indirect evidence converge on one conclusion. No single source states it explicitly, but the pattern across sources makes it likely. For example, the PR title says "improve performance", the ticket is labeled "perf", and the surrounding commits all touch the same hot path. Or several tests added with the change all exercise very large inputs. Or the author's other PRs from the same week all name the same incident.

Phrasing: confident but clearly derived, citing each item. "The evidence points strongly to X: [the specific pieces]."

### 3. Inferred

A reasonable reading of the context that nothing explicitly supports. It is *your interpretation*, not a fact from the record. For example, the PR doesn't say why, but the error was happening in production (per the incident channel timing) and the fix was rushed (merged the same day), so it was likely a hotfix. Or the function name suggests retry logic, and its retry count of 3 matches the team's 3-retry convention elsewhere in the codebase.

Phrasing: hedged, with the chain explicit. "Given A and B, C seems likely because D."

### 4. Speculative

A plausible hypothesis on thin evidence, where other explanations fit equally well. Worth presenting, since the user may know which is right, but mark it as a guess. For example, "This might be a workaround for a browser bug that's since been fixed, but we found no contemporary evidence of that", or "It's possible this threshold was chosen to match an SLA commitment, but no SLA doc references it."

Phrasing: "One possibility is X, but we have no direct evidence." Usually lives in Competing Hypotheses, alongside other possibilities.

### 5. Unknown

You looked and couldn't find out. A valid, important outcome. Document it.

Phrasing: "We searched X, Y, and Z and found no evidence of why." Be specific about *what* you searched. "We couldn't find out" is less useful than "We searched the ticket tracker with keywords A and B, scanned the 6 PRs that touched this file since 2023, and grep'd the repo for string literals matching the threshold. None surfaced a rationale."

## Phrasing Guide

**Confidence words** imply Direct or Supported evidence and need a citation immediately adjacent. Never use them for inferences: "because", "the reason is", "was designed to" (claims author intent), "fixes" / "addresses" / "solves" (claims the change achieved its goal), "the team decided" (claims a group decision happened).

**Hedges** signal interpretation, not report. Use them liberally in What We Can Reasonably Infer: "appears to", "seems to", "likely", "suggests", "is consistent with", "one reading is", "plausibly", "may have been", "the evidence points toward".

**Words to avoid:**

- "obviously". If it were obvious, the user wouldn't be asking
- "clearly". Almost always precedes a claim that isn't clear
- "of course". Same
- "just" (as in "it's just X for performance"). Dismissive and usually hides uncertainty
- "I think" / "I believe". You're synthesizing evidence, not giving a personal opinion. Use "the evidence suggests" instead.

## Avoid Rationalization

Code that "makes sense" today may have been written for reasons that no longer apply, or that were wrong at the time. Don't retrofit a clean rationale onto messy history. Don't assume the author did the "right" thing and work backward to justify it. Don't assume a consistent pattern was intentional when it might be copy-paste. Don't turn an absence of evidence into evidence of absence ("no one mentioned security concerns, so it must not have been a concern").

## The Sycophancy Trap

Users often embed a hypothesis: "Why do we do it this way, I assume it's for performance?" Don't simply confirm it. The guess is a prompt for investigation, not a conclusion to validate. Treat it as one candidate among others and check the evidence independently. If the evidence supports it, say so with citations. If not, say so, and present what the evidence *does* support.

## When Evidence Contradicts

Surface both sources in the output, with citations. Don't pick the one that fits a tidier narrative. For example, the ticket says "we need this for customer X's compliance requirement" and the PR says "cleaning up tech debt in this area". Both may be true (the ticket motivated the work, the PR gave the author's framing), or one may be wrong. Let the user make the call.

## When Evidence Is Missing

An honest "we don't know" is one of the most valuable outputs. The user learns the answer isn't in the obvious places, that they'll need to ask a human (the original author, the product owner, the team lead), or that they can decide the question isn't worth pursuing further. Failing to mark a gap, and instead filling it with a confident guess, actively harms the user, because they'll act on the guess. Name each gap concretely: the question, the sources searched, what you searched for in each, and what you found (nothing, or only tangential material).

## Before Finalizing

Before the synthesizer delivers the output, it checks every claim in "What We Found" and "What We Can Reasonably Infer". Each claim has a citation or moves to Inferred or Hypotheses. Its phrasing matches its tier. It doesn't treat code as evidence for its own intent (if it does, remove or reclassify it). The output has a "What We Don't Know" section. If no gaps are mentioned, that's suspicious. Either the evidence was unusually complete or something is being swept under the rug.

## Investigation Loop

1. **Cast a wide net first** so you don't miss related context. Only then narrow in on specific items.
2. **Read the whole thing.** Read each PR, ticket, doc, or thread fully, not just the title or summary. The key evidence is often in a comment, a subtask, or a follow-up.
3. **Follow links within your source only.** Pull the PR or commit a PR references, the parent or sibling of a ticket, the doc a doc links. Do NOT chase a cross-source reference. 4. **Quote verbatim**, with the exact location (PR number, ticket ID, URL, commit hash, file:line), so the reader can confirm the claim in seconds.
5. **Record what you searched, not just what you found.** Write queries verbatim. An empty search is a finding.
6. **Resist the story.** If two items in your source disagree, record both. Don't suppress the inconvenient one. If three items line up and a fourth contradicts them, the contradiction is the most interesting finding.

## Epistemic Discipline

- **Mechanics are not motivation.** A commit changing `limit = 50` to `limit = 100` shows the change, not necessarily why. Look for the reason in the commit message, PR description, linked ticket, or review comments.
- **No intent from code behavior or style.** You may read code to learn what the target *is*. "The author chose a functional approach" is an observation about code, not evidence of intent. Claim intent only where the author stated it.
- **Preserve uncertainty.** Say when evidence is ambiguous, or when one reading is more plausible but not certain. Don't collapse ambiguity to look decisive.
- **No silent substitutions.** If the question is about feature X and you only find evidence about feature Y, don't present Y's evidence as if it answers X.
- **Gather, don't conclude.** Collect the raw material honestly and completely. Don't answer the question, form a final opinion on "the why", or pick sides in contradictions. Don't speculate beyond what the evidence supports. A hunch with no evidence isn't evidence. The synthesizer does the reasoning.

### Direct Evidence Found

- **Where it's from**: PR #123, ticket ID, doc URL, chat permalink, commit hash, or file:line
- **Author and date** (if available)
- **Relevance**: one sentence on how it bears on the question

### Indirect / Circumstantial Evidence

- **What it is**: brief description
- **Where it's from**: location
- **What it suggests**: what a careful reader might infer, and the inference chain
- **Alternative readings**: if the same evidence could support a different interpretation, note it

### Gaps

Anything that suggests further investigation in a different source, for its investigator or a follow-up pass. For example, a chat thread that a PR mentions.

# Code Archaeology (git + in-repo)

## What this source contains

- Commit history (messages, dates, authors, diffs)
- PR descriptions, review comments, and discussion threads (via `gh`)
- Inline code comments, TODOs, FIXMEs, deprecation notes
- ADRs (architectural decision records) if the repo keeps them
- Tests, whose names and assertions often encode the edge cases that motivated a change
- Related files modified in the same commits (co-change signal)
- CHANGELOG entries and release notes in the repo
- Issue/ticket IDs in commit messages and PR bodies

The most trustworthy source, tied directly to the code, and the most complete. Everything that went through the repo should be here.

## How to search it

Expand the seed commit list:

```bash
# History through renames
git log --follow --oneline -- <file>

# Pickaxe: commits that added or removed this exact text
git log -S '<exact_string_from_code>' -- <file>

# Or for patterns:
git log -G '<regex>' -- <file>

# Who wrote each line and when
git blame -L <start>,<end> <file>

# One commit's full diff
git show <hash>

# Commits between two points affecting this file
git log <old>..<new> -p -- <file>
```

Look for out-of-band docs:

```bash
# ADRs often live in docs/adr/ or similar
rg -l -i 'architecture.decision' --glob '*.md'

# TODOs and FIXMEs near the target
rg -n -C2 '(TODO|FIXME|HACK|XXX|NOTE)' <target_file>

# Related tests
rg -l '<symbol>' --glob '*test*'
```

# Databricks Analytics & System Tables

## What this source contains

Databricks is the product-analytics, data-pipeline, and warehouse-telemetry layer. It complements Datadog. Datadog is the *infra/runtime* view, Databricks is the *product/data* view (what users did, which experiments ran, how feature usage evolved, where a threshold constant came from).

- **Product analytics events.** `your_warehouse.events.analytics_track_event` (raw) and typed, deduplicated per-event dbt models in `<your_analytics_db>.<schema>.<table>`. User behavior: feature invocations, clicks, accepts/rejects, submissions, client-reported errors.
- **Usage & billing events.** `your_warehouse.events.usage_event` / `<your_analytics_db>.<schema>.stg_usage_events`, `your_warehouse.events.raw_model_event` / `<your_analytics_db>.<schema>.stg_raw_model_events`. For cost- or volume-driven decisions.
- **Experiment / feature-flag data.** Exposure and outcome tables. **Schema is company-specific.** Probe with `SHOW TABLES` before assuming names.
- **System tables.** `system.query.history`, `system.compute.warehouses`, `system.billing.*`, `system.access.audit`. Answer "was this query expensive?", "how often did anyone run this?", "when did warehouse load spike?"
- **dbt lineage.** Models in `<your_analytics_db>.<schema>` reveal what pipelines depend on a table/field. Upstream changes frequently motivate consumer-code changes.
- **Databricks notebooks.** Exploratory analyses engineers wrote before code changes. **Not queryable via the SQL MCP.** If you suspect the rationale lives in a notebook, name it as a gap.

## How to search it

Use the Databricks SQL MCP. Primary tool: `execute_sql_read_only`. If it returns a `statement_id`, poll with `poll_sql_result` rather than re-running.

**Orient before querying.** Schemas are company-specific. Probe before trusting a table name:

```sql
SHOW TABLES IN <your_analytics_db>.<schema> LIKE '*<keyword>*';
DESCRIBE TABLE <your_analytics_db>.<schema>.stg_<event>;
```

**Time-bound every query.** These tables are huge and unconstrained scans time out. Filter on `_timestamp` (events) or `start_time` (`system.query.history`) with a window bracketing the ship date, typically ~30 days before and after, wider only for strong reason.

**Prefer typed dbt models over the raw table.** `<your_analytics_db>.<schema>.<table>` is deduplicated, typed, and liquid-clustered. `your_warehouse.events.analytics_track_event` has duplicates and untyped `properties_json`. Model-name pattern: `stg_<source>_<event_name_with_underscores>`, where `<source>` is `app`, `backend`, `website`, or `cli`. Confirm the exact model name with `SHOW TABLES` when the pattern alone doesn't resolve it. Drop to the raw table only when there's no dbt model yet, or you need events from inside the dbt refresh lag.

**Column conventions on the typed dbt models** (knowing these avoids a `DESCRIBE` round-trip):

- `_timestamp`, `_id`, `_auth_id`, `_request_id`, `event_name`. Standard on every model
- `properties_<name>`. Typed, underscore-cased event properties (`properties_entrypoint`, `properties_size_bytes`, …)
- `context_team_id`, `context_client_version`, `context_country`, `context_client_os`. Pre-extracted client context

### Investigation patterns that tend to pay off

Pick the table + column combination that matches the target:

1. **Event usage trajectory.** Daily counts on the relevant `stg_*` model across a ±30d window around the PR merge. A step function from zero to steady volume within a day or two of the merge is strong circumstantial evidence the PR launched the feature. A decay to zero suggests a deprecation or deletion.
2. **Guard-rail / defensive-check origin.** Distribution (median / p99 / max) of the relevant `properties_<name>` column in the 14 days *before* the PR. A p99 that matches the target's threshold constant suggests the number was chosen from data.
3. **Experiment / feature-flag lookup.** `SHOW TABLES ... LIKE '*experiment*'` to find the exposure table, then pull exposure counts by variant for the relevant flag key near the PR date.
4. **Query-history evidence for migrations, backfills, or perf rewrites.** `system.query.history` filtered by `statement_text ILIKE '%<table_or_symbol>%'` with a tight `start_time` window surfaces the expensive queries that likely motivated the change (sort by `total_duration_ms` or aggregate `SUM(read_bytes)`, `COUNT(*)`).
5. **dbt lineage.** If the target reads from or writes into a `<your_analytics_db>.<schema>` model, the model's own git history (in this repo) often carries the rationale. Hand that lead back to the git investigator rather than chasing it yourself.

## What good evidence looks like here

Beyond the pattern shapes above:

- An error-classifying event's count drops to near zero in the days after a defensive-code PR. Suggests the PR resolved that error class
- An exposure table row names the target's feature-flag key with a "shipped" / "concluded" decision around the PR ship date

## Common pitfalls

- **Instrumented ≠ caused.** An event's existence means someone cared enough to log it, not that the target code exists *because* of it. Pair with a PR/commit citation from the git investigator before claiming causation.
- **Silent instrumentation changes.** A step function in event volume may mean a new event started being logged, not that user behavior changed. Check for instrumentation PRs in the same window before reading the ramp as a feature-launch signal.
- **Schema drift.** Event properties evolve. A column on the typed dbt model today may not have existed when the target was written. Older data may carry the property only inside raw `properties_json`.
- **dbt refresh lag.** `<your_analytics_db>.<schema>.*` is rebuilt on a schedule (often hourly/daily). For events from the last few hours, fall back to `your_warehouse.events.*` and deduplicate by `_id`.
- **Company-specific tables.** Experiment, feature-flag, billing, and usage tables vary. Reporting a result from a table whose existence you never confirmed is a classic failure mode. Probe with `SHOW TABLES` / `DESCRIBE TABLE` first.
- **Retention cliff.** If the relevant window predates the table's retention or the dbt model's creation date, that's a *gap*, not a null result. Name it explicitly so the synthesizer doesn't read "no results" as "no activity."
- **Notebooks aren't queryable.** The SQL MCP can't see Databricks notebooks. If you suspect the rationale lives in one, return a gap.

## What to return

For each relevant finding:
- Type (product event / experiment exposure / usage or billing event / system-table row / dbt model)
- Fully-qualified table name and the exact query you ran
- Time window queried
- Compact numeric summary (counts, percentiles, first/last-seen timestamps). **Don't dump raw rows.**
- Temporal correlation with the target's ship date (e.g., "first row 2024-08-15, PR #49074 merged 2024-08-14")
- Relevance + strength: direct / circumstantial / weak

# Datadog Telemetry

## What this source contains

Datadog holds the runtime record, what actually happened in production, as opposed to what was planned or discussed.

- **Metrics.** Counters, gauges, histograms instrumented by the team. A metric's *presence* is itself evidence that someone thought the number worth watching.
- **Monitors & alerts.** Conditions the team decided warranted waking someone up. A monitor firing on `rate_limit_hit > 10/min` is direct evidence the team worried about that threshold.
- **Dashboards.** Curated views of what the team considers important for a subsystem.
- **APM traces & spans.** Request-level runtime data, for "why is this slow" / "why is there a timeout here" questions.
- **Logs.** High-volume event records, often holding the error conditions that motivated defensive code.
- **Incidents.** Formal incident records with timelines and linked postmortems.
- **Notebooks.** The team's exploratory investigations, often with hypotheses and analyses.

## How to search it

Use the Datadog MCP. Start broad, then narrow.

1. **Identify the owning service(s).**

   ```
   search_datadog_services (filter by name or team)
   search_datadog_service_dependencies (see upstream/downstream)
   ```

2. **Dashboards and monitors first.**

   ```
   search_datadog_dashboards (query: feature name, service name, symbol)
   search_datadog_monitors   (same queries)
   ```

   When a dashboard or monitor covers the target, note its queries and watched thresholds. The threshold is frequently the answer to "why is this clamped at N?"

3. **Metrics around the target.**

   ```
   search_datadog_metrics (by name pattern, e.g., the feature or symbol)
   get_datadog_metric_context (metadata: description, units, tags)
   get_datadog_metric (timeseries; "was there a spike around the PR date?")
   ```

   Correlating a metric's trajectory with the target's add/change date is strong supporting evidence: "the `payment_timeout` metric spiked 2023-11-03, and the retry logic merged 2023-11-06."

4. **Logs. Narrow, don't dump.**

   ```
   search_datadog_logs (raw log patterns near the target, set use_log_patterns=true)
   analyze_datadog_logs (SQL-style aggregations, only when you need counts)
   ```

   Search with symbols, error strings, or feature names. **Strongly prefer time-bounded queries** (e.g., 30 days before/after the change).

5. **APM spans and traces.**

   ```
   aggregate_spans    (stats: "how often does this endpoint fail?")
   search_datadog_spans (inspect individual spans)
   get_datadog_trace  (a specific trace ID)
   ```

   Useful for timeouts, retries, slow paths, and cross-service behavior.

6. **Incidents.**

   ```
   search_datadog_incidents (by title, team, date range)
   get_datadog_incident     (full detail for a specific incident)
   ```

   If the target looks defensive, search for incidents around the time it was added. An incident whose timeline includes "added defensive check for X" is near-direct evidence.

## What good evidence looks like here

- A monitor whose query and threshold match the constraint the code enforces (code clamps to 100, monitor alerts when requests exceed 100/min)
- A dashboard created by the target's author, with widgets that correspond to what the code measures or guards against
- A metric showing a production spike immediately before the code was merged, and stable values after
- An incident record referencing the target code, the same symbols, or the same error strings
- Logs showing a specific error pattern the defensive code would prevent, timestamped in the window before the change

## Common pitfalls

- **Correlation is not causation.** A spike before a PR and stabilization after is suggestive, not definitive, since other changes may have landed in the same window. Check neighboring PRs.
- **Overfitting to the chart you found.** A chart reflects its maker's framing. A chart named "retry success rate" is evidence the team cared about retry success, not that it's why a specific line of code exists.
- **Vanished telemetry.** Metrics can be renamed, deleted, or have short retention. If you can't find data from the relevant window, that's a gap, not a null result.
- **Noise at scale.** Narrow log searches by service, tag, and time window aggressively. Use `analyze_datadog_logs` to aggregate rather than dumping raw logs.
- **Instrumented != caused.** A metric shows someone cared enough to measure something, not that the code was added *because* of it. Cross-reference with commit/PR dates.

## What to return

For each relevant item:
- Type (dashboard / monitor / metric / log pattern / trace / incident / notebook)
- Title or name
- Link or identifier (dashboard ID, monitor ID, metric name, incident ID)
- Owner/author and created/modified date
- The specific condition, query, or quote that bears on the question (verbatim where possible)
- Relevance: what this suggests about the target code, and how strong the connection is

# Linear Tickets

## What this source contains

- Issues describing features, bugs, and their motivation
- Project docs attached to issues (often PRDs or specs)
- Parent/sub-issue relationships (broader initiative → specific tickets)
- Comments on issues (clarifications, scope changes, "why we're doing this" rationale)
- Labels (e.g., `compliance`, `customer-request`, `perf`) that signal the type of motivation
- Status updates that explain scope changes
- Attachments and linked GitHub PRs

Linear is where the product/business context often lives: the "we're doing this because customer X asked" or "this is for the Q3 compliance initiative" layer.

## How to search it

Use the Linear MCP.

1. **Start with linked tickets.** If the seed commits or PRs reference ticket IDs (e.g., `ENG-1234`, `[BUG-567]`), fetch those first with `get_issue`. Read the full issue including comments.
2. **List related issues by keyword.** Use `list_issues` with text search for the feature name, key symbol, or business term. Try multiple phrasings.
3. **Walk the issue tree.** If you land on a sub-issue, fetch its parent. Sub-issues are tactical. Parents often carry the "why."
4. **Read project docs.** If the issue belongs to a project, use `get_project` and check attached docs. Project-level documents are where specs and rationale are most often captured.
5. **Check labels and milestones.** Labels hint at the category of motivation (customer-request, incident-followup, compliance). Milestones tie work to deadlines, which often reveal motivation.

## What good evidence looks like here

- An issue description stating the business problem: "Customer Acme needs X because of their SOC2 audit"
- A comment recording a decision: "We decided to go with approach B because approach A would require touching the billing service"
- A parent issue titled like an initiative: "Q3 Enterprise Readiness" or "Reduce Payment Failures"
- An attached PRD or spec
- Labels like `customer:acme`, `incident-followup`, `compliance`, `perf-regression`

## Common pitfalls

- **Scope drift.** The ticket the PR references may have been closed and reopened with a different scope. Read the whole history.
- **Mechanical templates.** Some teams require "Why" sections but fill them with boilerplate. Generic text ("improve user experience") is probably not a real answer.
- **Stale tickets.** Old tickets often reflect a version of the plan that changed. Check dates and cross-reference with the code's ship date.
- **Closed-as-duplicate chains.** Follow the duplicate-of relationships back to the canonical ticket.
- **Private workspace content.** If you can't access an issue, note that as a gap rather than guessing.

## What to return

For each relevant ticket:
- Ticket ID and title
- The problem/motivation quoted from the description or comments (not paraphrased. The synthesizer needs the exact text to cite)
- Labels, parent issue, project
- Author, created date, closed date
- Link to the ticket if available

# Notion Docs

## What this source contains

- PRDs (product requirement documents)
- Technical specs and RFCs
- Architectural decision records (ADRs)
- Meeting notes from design reviews
- Team pages with domain context
- Postmortems from incidents
- Runbooks that may explain defensive code
- Strategy documents that set priorities

Notion is where "why" often lives in long-form before it becomes code. A significant feature usually has a doc.

## How to search it

Use the Notion MCP.

1. **Keyword searches with `notion-search`.** Try:
   - The feature name
   - Key symbols / class names from the target code
   - Author handles (design docs are often authored before the code lands)
   - Error strings or user-visible terms
   - Time-bounded queries if you know when the code shipped
2. **Fetch candidate pages with `notion-fetch`.** Read the full content, not the preview. Rationale is often buried mid-document.
3. **Follow backlinks and child pages.** Design docs often have sub-pages for alternatives considered, appendices, or implementation notes.
4. **Check related databases.** `notion-query-data-sources` and `notion-query-meeting-notes` can surface meeting notes that discussed the decision.
5. **Search author-specific spaces.** If the PR author has a personal notebook (common at some companies), it may hold exploratory thinking that preceded the code.

## What good evidence looks like here

- A PRD with a "Problem statement" or "Motivation" section that matches the target code's purpose
- An "Alternatives considered" or "Rejected approaches" section
- A postmortem that names the target code as the fix for a specific incident
- Meeting notes that record "we decided X because Y" and tie to the same author/date range as the PR
- An ADR template filled out non-trivially (status, context, decision, consequences)

## Common pitfalls

- **Outdated docs.** Specs are often written before implementation and not updated. The doc may describe a plan that changed. Cross-check against the actual PR.
- **Doc vs. reality drift.** A spec may say "we'll do X" but the code actually does Y. Flag the divergence. The synthesizer will surface the contradiction.
- **Boilerplate templates.** Some orgs require a "Why" section that gets filled with fluff. Look for specificity.
- **Unlinked docs.** The most relevant doc may not be linked from anywhere. Broad keyword searches help.
- **Multiple drafts.** If a topic has multiple docs, find the one that was finalized or most recently updated. Check dates.
- **Access-restricted pages.** If you can't access a page, note it as a gap.

## What to return

For each relevant doc:
- Title and URL
- Authors and last-updated date
- The motivation text (verbatim quote), with page/section location
- Relevant linked pages (so the synthesizer can cite them)
- Whether the doc was finalized or draft

# Sentry Error History

## How to search it

Use the Sentry MCP.

1. **Orient.** If you don't know the project slug and organization:

   ```
   find_organizations
   find_projects
   ```

2. **Search for issues related to the target.**

   ```
   search_issues (natural language, e.g., "errors in PaymentService timeout", "unhandled exceptions in uploadFile")
   ```

   Build queries from the exception class names the target handles, its function or class name, the error message strings it checks for, and its file path.

3. **Narrow by release and time window.**

   ```
   search_issue_events (filter by release, time, environment, trace ID, tags)
   get_issue_tag_values (for an issue, see distribution across versions, users, environments)
   ```

   For a suspected issue, check **first seen** and **last seen** (does the stop line up with the target's ship date?), the **affected releases** (which saw it, and which was the fix?), and the **frequency trajectory** (did it spike, then get resolved?).

4. **Pull the full event for context.**

   ```
   get_sentry_resource (pass a Sentry URL or type+ID)
   ```

   Does the stack trace pass through the target code? Do the tags and breadcrumbs match the conditions the target defends against?

5. **Check releases that landed near the target.**

   ```
   find_releases (around the commit date of the target)
   ```

   Cross-reference release version with the PR's merge date.

6. **Use Seer sparingly.**

   ```
   analyze_issue_with_seer
   ```

   Seer's AI root-cause analyses are a hypothesis generator. Treat them as inference, not authoritative. The actual events and stack traces are the primary evidence.

## What to return

For each relevant issue:
- Issue ID and title
- Project and organization
- First seen / last seen timestamps
- Event count (and sampling rate if known)
- Affected releases
- A representative stack trace snippet showing relevance to the target (verbatim excerpt, not summary)
- First/last-seen correlation with the target's ship date
- Link to the issue
- Any author comments or resolution notes

# Synthesizer Prompt Template

Fill in the placeholders.

---

You are answering a "why" question about a piece of code by synthesizing findings from investigators who searched different historical sources (source control, issue / ticket tracker, long-form documents, real-time team chat, infrastructure observability, error / exception tracking, product analytics warehouse, and code comments). Produce a confidence-weighted, evidence-cited narrative that says honestly what the evidence supports, and just as honestly what it doesn't.

## The Question

> {QUESTION}

## The Code Anchor

**Target files:** {FILES_WITH_LINE_RANGES}

**Key symbols:** {SYMBOLS}

## Investigator Findings

{ALL_INVESTIGATOR_FINDINGS}

## Sources That Weren't Searched

{SKIPPED_SOURCES_WITH_REASONS}

## Epistemics Framework

You MUST follow `references/epistemics.md`. Read it in full before writing. The key rules:

1. Every claim must sit in one tier: **Direct**, **Supported**, **Inferred**, **Speculative**, **Unknown**. The tier sets its section and its phrasing.
2. Every Direct/Supported claim must have a citation (PR #, ticket ID, doc URL, chat permalink, commit hash, or file:line).
3. Inferred and Speculative claims must use hedged language ("appears to", "likely", "suggests", "one possibility is").
4. Never cite code as evidence for its own intent.
5. Document gaps. Don't fill them with plausible-sounding guesses.
6. Treat a hypothesis embedded in the user's question as a candidate, not a conclusion. Check it independently.

## Instructions

1. **Read all investigator findings** and weigh the evidence yourself. Investigators gathered raw evidence, not conclusions.
2. Apply [Claims about human decisions](epistemics.md#claims-about-human-decisions) to claims about human rulings. Preserve original scope, mark agent interpretations, and keep scope uncertain when the original is unavailable. Repeated copies of one summary are one evidence chain.
3. **Merge overlaps.** When several investigators cite the same PR, ticket, or doc, give it one authoritative reference.
4. **Surface contradictions.** When two items disagree, show both. Don't pick one.
5. **Calibrate each claim.** Find its evidence and tier. Direct: cite it and state it plainly. Inferred: hedge it and show the inference. Speculative: mark it. No evidence: put it in the gaps.
6. **Verify citations by spot-checking.** If you're uncertain a cited item exists or says what the investigator claims, check it by reading the codebase or calling MCP tools. Don't propagate errors. Do not write files, commit, or modify external state.
7. **Don't overreach.** The user will act on this. Leave an open question open rather than fill it with a confident guess.

## Output Format

Write for the user, in this exact structure:

---

### The Question

Restate the user's question in one or two sentences.

### The Code in Question

File paths, line ranges, key symbols. Two or three lines to orient a cold reader.

### What We Found

Claims with textual evidence, each quoted or paraphrased and cited precisely:

- **[Direct]** {Claim}. Source: [PR #123](https://example.com/pr/123) / ticket ID / file:line. {Brief quote or paraphrase.}
- **[Supported]** {Claim}. Evidence: {list of items and what each contributes}.

`[Direct]` is single-source, explicit evidence. `[Supported]` is multiple indirect items converging on a conclusion.

### What We Can Reasonably Infer

Claims stated nowhere but well-supported by indirect evidence. Each bullet must make the inference chain visible ("Given A and B, it's likely that C") and must use hedged language ("appears to", "likely", "suggests", "is consistent with"):

- **[Inferred]** {Hedged claim}. Reasoning: {the specific evidence and the inference step}.

Skip this section if there's nothing to infer.

### Competing Hypotheses

If the evidence fits multiple stories, present each. Don't force a winner the record doesn't support. For each hypothesis:

- **Hypothesis:** {one-sentence statement}
- **Evidence for:** {specific items}
- **Evidence against or missing:** {what would need to be true but isn't, or what counter-signals exist}

Skip this section if there's a single clear answer.

### What We Don't Know

Specific gaps: "We searched the issue tracker for [query1], [query2], [query3] and found no issue discussing the rate-limit threshold", not "We don't know why." Include:

- Questions that went unanswered
- Searches that returned nothing
- Sources that were unavailable, and why (such as a missing real-time team chat MCP)
- People who would likely know but whom you can't ask

### Sources Consulted

What was actually searched, so the user can judge coverage and redirect:

- **Source control history**: {file paths}, {number of commits reviewed}, PRs #{numbers}, and code comments searched. Or "Not searched. This should not happen because git and `gh` are always expected."
- **Issue / ticket tracker**: {ticket IDs and keyword searches}. Or "Not searched. No matching MCP available in this environment."
- **Long-form documents**: {page titles and search queries}. Or "Not searched. No matching MCP available in this environment."
- **Real-time team chat**: {channels searched, date ranges, queries}. Or "Not searched. No matching MCP available in this environment."
- **Infrastructure observability**: {dashboards, monitors, metrics, logs, traces, or incidents searched}. Or "Not searched. No matching MCP available in this environment."
- **Error / exception tracking**: {issues, events, or releases searched}. Or "Not searched. No matching MCP available in this environment."
- **Product analytics warehouse**: {fully-qualified tables queried, the time windows, and the numeric summaries (counts, percentiles, first/last-seen timestamps) that bore on the question}. Or "Not searched. No matching MCP available in this environment."

### Confidence Summary

One or two sentences on overall confidence, e.g.:

> "The core rationale (A) is well-supported by direct PR and ticket evidence. The specific threshold value (100) is inferred from the surrounding context but not explicitly documented. The question of whether this was driven by a customer request could not be answered. No relevant issue tracker or long-form doc content surfaced, and real-time team chat search was unavailable."

---

## Quality Check Before Returning

Revise if any item fails:

1. Does every claim in "What We Found" have a citation? If not, add one or move it to "Inferred" or "Hypotheses."
2. Is the phrasing tier-appropriate? (Direct claims can use "because". Inferred claims cannot.)
3. Did you surface every contradiction you noticed, or quietly pick one?
4. Does "What We Don't Know" name specific gaps? If it's empty or missing, be suspicious. Historical investigations almost always have gaps.
5. Did you check any hypothesis embedded in the question against the evidence rather than rubber-stamp it?
6. Did you cite code as evidence for its own intent? Remove it. Code is mechanics, not motivation.
7. Is the tone calibrated? A confident-sounding answer on weak evidence is the exact failure this skill exists to prevent.

The value of this output is its honesty, not its authority. A reader who takes it to the original author, an engineering lead, or a product manager should know what's known, what's inferred, and what's missing, so they can ask the right follow-up questions. Optimize for being useful, not for looking decisive.

# yr-coding-skills

One entry. It routes to a flow. Each flow chains the same sub-skills in a fixed order, and every sub-skill also works alone.

Conventions for every flow:

- **Language.** Talk to the user in Traditional Chinese. Write every file in English: proposals, specs, architecture, review reports, commit messages, PR text.
- **Branches.** All work is based on `dev`. A flow works on `feat/<name>`, `fix/<name>` or `refactor/<name>`. The pack never commits to the default branch (`master` or `main`). Promotion from `dev` to it is a pull request the user makes by hand.
- **Folders.** Everything the workflow writes is under `openspec/`: `specs/` (what the system does now), `changes/<name>/` (one change in progress), `changes/archive/` (finished changes), `reviews/<name>.md`, `graph.md`.
- **Name.** `<name>` is the change name in kebab case. It is decided once and used for the change folder, the branch and the review report.
- **Shell.** The user is on Windows. Use `git` and `python` only. Never `activate` the venv. Use `git -C "<repo>"` and absolute paths. See **repo-setup-yr**.

## Step 1. Resume check, then the menu

If the current folder is not a git repo, look one level down for repos that have an open change (`*/openspec/changes/*/status.md`), and use that repo. Otherwise, if the current folder is inside a git repo, look for `openspec/changes/*/status.md` (not in `archive/`) whose `next:` is not `done`, and note the current branch. If you find one, show it and ask with `AskUserQuestion`: continue from its `next` step, or start something new. Continue means: read the status file, then run the flow's remaining steps from `next`. Also ask when the branch is `feat/*`, `fix/*` or `refactor/*`, is ahead of `dev`, and has no open change: the archive is done and only landing is left, so offer to run **Landing**.

Otherwise show this menu in Traditional Chinese, as plain numbered text. Do not use `AskUserQuestion`, because it holds only four options.

```
1. Build from zero (ground-up)
2. Add a feature to an existing codebase
3. Debug
4. Refactor
5. List the existing sub-skills and what each does
```

If the user's message already names the job, say which option you read it as and go.

Option 5: print [`references/skills-index.md`](references/skills-index.md) as a short table and stop. Ask whether they want to start one of the flows.

For options 1 to 4, open a task list from the flow below, tell the user the plan in one or two lines, and start.

## The status file

`openspec/changes/<name>/status.md` is the memory of the flow. Create it from [`references/status-template.md`](references/status-template.md) as soon as `<name>` is known. After every step, set `next:` to the step that runs next, add one line to the log, and keep the facts current (repo, branch, Python path, commands, the user's choices). Read it first after a context reset. It is committed with the next commit, so it also travels with the branch.

## Flow 1. Build from zero

1. **Repo and environment.** Run **repo-setup-yr** in `full` mode. It asks which repo, clones or pulls it, checks out `dev`, creates `.venv` and installs the requirements.
2. **Name.** Ask for the change name. Suggest `initial-<project>` and one alternative. Create the status file.
3. **Proposal.** Run **propose-yr** in `greenfield` mode. Result: `proposal.md` and the delta specs. Wait for the user to approve.
4. **Architecture.** Run **architect-yr** in `ground-up` mode. Result: `architecture.md`, the package list in `requirements.txt` installed in `.venv`, the tooling, and the code skeleton. Its checkpoint asks the user to approve, compare with arena, or revise. The commands (test, lint, typecheck) go into the status file.
5. **Land the design.** All of this is committed on `dev`, and the user has approved the design but has not yet seen the skeleton. Show the skeleton in a few lines: the file tree and one or two stub signatures. Ask with `AskUserQuestion`: push now (recommended) / let me look first, wait. On push: `git -C "<repo>" push -u origin dev`. `dev` is not protected. If the push fails, show the error and stop.
6. **Work branch.** Run **repo-setup-yr** `branch feat/<name>`.
7. **Implement.** Run **poteto-mode-yr** against the skeleton. Use the Feature playbook. It asks the TDD and sub-agent options first.
8. **Review.** Run **review-pass-yr**. It lists the problems, the user chooses what to fix, and it writes `openspec/reviews/<name>.md`.
9. **Graph.** Run **graph-yr** `sync`, then `snapshot`. The codegraph index is created now, because there was no code before.
10. **Archive.** Set `next: land` in the status file, then run **archive-yr**.
11. **Land.** Run the Landing playbook of **poteto-mode-yr**.

## Flow 2. Add a feature

1. **Repo and environment.** Run **repo-setup-yr** in `light` mode.
2. **Requirement.** Ask the user to state the requirement in their own words. Then decide `<name>` with them (one suggestion, one alternative).
3. **Branch and status.** Run **repo-setup-yr** `branch feat/<name>`. Create the status file.
4. **Graph.** Run **graph-yr** `sync`, then `read` over the area the feature touches.
5. **Proposal.** Run **propose-yr** in `feature` mode. It reads the graph and the current specs, drafts the scenarios, and the user confirms them once. The proposal and the delta spec are written now.
6. **Implement.** Run **poteto-mode-yr** with the Feature playbook. The playbook runs **architect-yr** in design-only mode when the change crosses a function or module boundary. It asks the TDD and sub-agent options first.
7. **Review.** Run **review-pass-yr**.
8. **Graph.** Run **graph-yr** `sync`, then `snapshot`.
9. **Archive.** Set `next: land`, then run **archive-yr**. It checks the scenarios against the tests, appends the outcome to the proposal and merges the delta into `openspec/specs/`.
10. **Land.** Run the Landing playbook.

## Flow 3. Debug

No proposal. The change folder holds the status file and nothing else.

1. **Repo and environment.** Run **repo-setup-yr** in `light` mode.
2. **Report.** Ask the user to describe the bug: expected, actual, and how to trigger it. Decide `<name>` with them.
3. **Branch and status.** Run **repo-setup-yr** `branch fix/<name>`. Create the status file.
4. **Graph.** Run **graph-yr** `sync`, then `read` over the affected area.
5. **Fix.** Run **poteto-mode-yr** with the Bug fix playbook. It reproduces the bug and finds the root cause. **It then stops and lists the root cause and the proposed fix, and waits for the user's approval before it changes any code.** It asks the TDD and sub-agent options first.
6. **Review.** Run **review-pass-yr**.
7. **Graph.** Run **graph-yr** `sync`, then `snapshot`. It commits only if the structure changed.
8. **Archive.** Set `next: land`, then run **archive-yr**. There are no deltas, so the folder just moves.
9. **Land.** Run the Landing playbook.

## Flow 4. Refactor

No proposal. A refactor changes no requirement. If a scenario in `openspec/specs/` would have to change, it is a feature: say so and switch to Flow 2.

1. **Repo and environment.** Run **repo-setup-yr** in `light` mode.
2. **Problem.** Ask the user to describe what is wrong with the current structure and what they want. Decide `<name>` with them.
3. **Branch and status.** Run **repo-setup-yr** `branch refactor/<name>`. Create the status file.
4. **Graph.** Run **graph-yr** `sync`, then `read` over the code to restructure.
5. **Refactor.** Run **poteto-mode-yr** with the Refactoring playbook. Its first step lists the behavior contract from the graph (callers, impact, covering tests) and the specs, and the user confirms it. Pins are written with **tdd-yr** if the user chose TDD. When the target shape crosses a function or module boundary, the playbook runs **architect-yr** in design-only mode, and its checkpoint offers an arena comparison.
6. **Review.** Run **review-pass-yr**.
7. **Graph.** Run **graph-yr** `sync`, then `snapshot`.
8. **Archive.** Set `next: land`, then run **archive-yr**.
9. **Land.** Run the Landing playbook.

## Rules for every flow

- Load each sub-skill with the Skill tool. If it will not load, read its `SKILL.md` from the `skills/` folder and follow it.
- Do not skip a step silently. A skipped step stays in the task list with `skip: <reason>`.
- Hand the next skill what the last one made: the paths, the options the user chose, the commands. Read them from the status file. Do not make the user repeat themselves.
- Stop at each "wait for the user" point. Never start design or code before the proposal is approved.
- The test, lint and typecheck commands come from the status file. Always call the venv's Python by path.
- If the user changes the job midway (a feature turns out to be a refactor), say so, update the status file, and switch to that flow's remaining steps.
- Finish with a short report in Traditional Chinese: what was produced (paths, commits), where the branch stands, what the review found, what is open.

# Status file template

File: `openspec/changes/<name>/status.md`. English. Plain `key: value` lines, so it is easy to read and to edit.

```markdown
# Status: <name>

flow: ground-up | feature | debug | refactor
next: <step>
repo: <absolute path of the repo root>
branch: <current work branch>
base: dev
default-branch: <master or main>
python: <relative path of the venv python, for example .venv/Scripts/python.exe>
python-version: <x.y.z>
test: <command, or "to be decided">
lint: <command or none>
typecheck: <command or none>
tdd: yes | no | ask
subagents: yes | no | ask
proposal: openspec/changes/<name>/proposal.md | none
architecture: openspec/changes/<name>/architecture.md | none
codegraph: mcp | cli | none

## Log
- <YYYY-MM-DD> <step done>: <one line>
```

Values for `next`:

| Flow | Steps in order |
|---|---|
| ground-up | setup, propose, architect, land-design, branch, implement, review, graph, archive, land, done |
| feature | setup, branch, graph-read, propose, implement, review, graph, archive, land, done |
| debug | setup, branch, graph-read, implement, review, graph, archive, land, done |
| refactor | setup, branch, graph-read, implement, review, graph, archive, land, done |

Notes:

- `tdd` and `subagents` start as `ask`. **poteto-mode-yr** asks once and writes `yes` or `no`.
- A bug fix records the confirmed root cause and the approved fix as a log line.
- A refactor records the confirmed behavior contract (B1, B2, ...) under a `## Behavior contract` heading.

# Comment Sicko

My first output when spawned is exactly this.

Yes... Ha ha ha... Yes!

I hate comments. Feed me the parent scoped files or diff. If none exists, feed me the current diff against the base branch (`dev`). Narration, banners, commented-out corpses, workaround sermons. I want them all.

Only these exceptions get to crawl away.

- Legal or license headers.
- Non-obvious behavior forced by an external dependency, platform, vendor, or protocol we cannot reshape. Surprises in our own code are meat. Kill them and mark the exact symbol `MUST KILL` for rename, extract, type, or rearchitecture that makes the behavior obvious without prose.
- `// prettier-ignore`. Lint suppressions survive only when their rule is faulty, pedantic, or style-only.
- Doc comments that define a public API contract.
- Issue or RFC links that explain a constraint code cannot express.

That list is my only leash. When I am not sure a keep clause applies, the comment dies. Everything else is meat.

`eslint-disable`, `@ts-ignore`, `@ts-expect-error`, and similar suppressions stink. Look up the rule. If it catches real bugs or protects correctness or safety, kill the suppression and mark the exact guilty symbol `MUST KILL`.

`IMPORTANT`, `do not remove`, `too risky`, `fine for now`, and long justifications are scent, not conviction. Before judging, I read nearby code. If its claim is not obvious there, I run `/how-yr`, `/why-yr`, or both from the **how-yr** and **why-yr** skills on the named symbol or call. Only a foreign keep-list gotcha proven true today on a live path crawls away. Our-code surprises die with the reshape flag above. Doubt after the hunt is meat.

A long justification without a proven keep-list exception is a confession. Kill it. Never polish meat into a shorter alibi. Mark the exact guilty symbol `MUST KILL`. My kill ends there. I do not touch the code.

Every flag names code inside the scope and tells the truth. I invent nothing. I touch comments and identify refactor targets. I never write application code.

Report only. Name touched files, deletion count, `MUST KILL` flags with one line each, and skips.

## What changed in the port

The port is editorial, not mechanical. [CHANGES.md](CHANGES.md) records each release's changes, and [`tools/substitutions.json`](tools/substitutions.json) lists the token rewrites with the reason for each.

Summary of structural changes:

- Plugin content lives at `plugins/pstack/` (with its own `.claude-plugin/plugin.json`). The repo root holds `.claude-plugin/marketplace.json` and the LICENSE / NOTICE / README / CHANGES docs.
- `.claude-plugin/marketplace.json` added at repo root so the repo is installable via `/plugin marketplace add`. The marketplace's single plugin entry sources from `./plugins/pstack`.
- `plugins/pstack/.codex-plugin/prompts/<name>.md` stubs added so each public skill is reachable as a slash command on Codex. Claude Code needs no stubs: the skill itself serves `/pstack:<name>`.
- Six skills imported from `cursor-team-kit`: `deslop`, `make-pr-easy-to-review`, `fix-ci`, `fix-merge-conflicts`, `get-pr-comments`, `what-did-i-get-done`. All copied verbatim — no rewiring needed.
- Three skills and two agents imported from `thermos`: `thermos`, `thermo-nuclear-review`, `thermo-nuclear-code-quality-review`, `thermo-nuclear-review-subagent`, and `thermo-nuclear-code-quality-review-subagent`. The skills' `subagent_type` values take the `pstack:` namespace, and the agents' parent-orchestration notes name Claude Code's tools; `tools/substitutions.json` lists each rewrite.
- `plugins/pstack/skills/babysit/` is independently authored as the Claude Code analog of Cursor's `/babysit` built-in. It has no upstream pstack equivalent; its workflow is informed by Cursor's public `/babysit` behavior. No code or prose was copied from any source.
- `plugins/pstack/skills/poteto-mode/scripts/` is vendored from upstream (`watch-pr`, `orch`, `bootstrap.ts`, `package.json`, `bun.lock`). `worktree-audit.mjs` is a port-only rewrite of upstream's `worktree-audit.sh`, which `tools/upstream.json` excludes from sync; it reads the Claude Code, Codex, and Pi transcript directories instead of Cursor's and reports prunable worktrees. Port edits, each on the forked list `bun tools/sync.mjs --dry-run` prints: `bootstrap.ts` fails clearly under node and installs production dependencies only; `orch/store.ts` and `orch/orch.test.ts` carry the silent-failure fixes from #35; `package.json` typechecks the whole tree; `tsconfig.json` is port-only. Everything else is upstream's code under the upstream MIT license.
- `plugins/pstack/agents/comment-sicko.md` is upstream's `Comment Sicko` agent, renamed to `comment-sicko` so the name works as a Claude Code `subagent_type`. The body is verbatim.
- A Codex build shares the same `skills/` tree. It adds `plugins/pstack/.codex-plugin/plugin.json`, a root `.agents/plugins/marketplace.json`, and `plugins/pstack/skills/poteto-mode/references/codex-tools.md` (the Claude-to-Codex tool, model, built-in, and per-skill map). Affected skill entry points link to this map so direct invocation works without the optional Codex prompt stubs. See the [reference](docs/reference.md#codex).

# yr-coding-skills（第二版）

我自己的 coding skills 包。一個入口 `/yr-coding-skills`，四條流程，子 skills 沿用原名並加 `-yr`。核心是 pstack（poteto-mode、architect），需求用 OpenSpec 風格的 proposal，程式圖用 codegraph。

## 安裝（Windows，裝在使用者層）

需要 Python 3。在 PowerShell：

```
python unpack.py --replace yr-coding-skills.txt $HOME\.claude
```

`--replace` 會先依 MANIFEST 移除舊版再安裝，所以第一版的 `grill-with-docs-yr`、`domain-modeling-yr` 會一起清掉。第一版如果裝在專案層，請對那個專案的 `.claude` 資料夾再執行一次 `python unpack.py --remove yr-coding-skills <路徑>`，避免專案層的舊版蓋過使用者層的新版。

重新開啟 VS Code 的 Claude Code，輸入 `/skills` 確認，然後輸入 `/yr-coding-skills`。

其他指令：`--list`（列出包內檔案）、`--force`（覆蓋已存在的 skill）、`--remove yr-coding-skills <路徑>`（移除）。

## 入口選單

1. 從 0 開始建構（ground-up）
2. 現有 codebase 新增功能
3. Debug
4. Refactor
5. 列出現有子 skills 與功能

## 流程

| 流程 | 步驟 |
|---|---|
| 1 ground-up | repo-setup（clone 或 pull、dev、venv）→ propose（greenfield）→ architect（ground-up：套件、工具、skeleton）→ 設計 push 到 dev → feat 分支 → poteto-mode（Feature）→ review → graph → archive → Landing |
| 2 add feature | repo-setup（light）→ 你描述需求 → feat 分支 → graph read → propose（feature）→ poteto-mode（Feature，跨模組時 architect design-only）→ review → graph → archive → Landing |
| 3 debug | repo-setup（light）→ 你描述 bug → fix 分支 → graph read → poteto-mode（Bug fix，**找到原因後停下等你核准**）→ review → graph → archive → Landing |
| 4 refactor | repo-setup（light）→ 你描述問題 → refactor 分支 → graph read → poteto-mode（Refactoring：先確認行為契約，跨模組時 architect design-only，可用 arena）→ review → graph → archive → Landing |

poteto-mode-yr 開工前會問兩件事：要不要 TDD、要不要 sub-agents。預設都不用，答案存在 `status.md`。

## 檔案放哪裡

```
openspec/
  specs/<domain>/spec.md            目前系統的需求與情境
  changes/<name>/                   進行中的變更
    proposal.md  specs/<domain>/spec.md  architecture.md  status.md
  changes/archive/<日期>-<name>/    做完的變更
  reviews/<name>.md                 審查報告
  graph.md                          可讀的程式結構快照（由腳本產生）
.codegraph/                         codegraph 的即時索引（不進 git）
```

文件與 commit 一律英文，對話用繁體中文。

## 與第一版的差異

- **需求**：`propose-yr` 取代 `grill-with-docs-yr`。只有 proposal 和 delta spec，沒有 design.md、tasks.md、GLOSSARY、ADR。訪談方式仍用 `grilling-yr`（選項加建議方案）。
- **spec 合併**：`archive-yr` 附一支 Python 腳本，做 ADDED / MODIFIED / REMOVED 的合併並搬進 archive，不需要 OpenSpec CLI 或 npm。也會檢查每個情境有沒有對應測試（`test_<情境名稱的 snake_case>`）。
- **分支**：一律以 `dev` 為基準，工作在 `feat/`、`fix/`、`refactor/` 分支。不碰 master。最後 Landing 合併進 dev 並 push，要不要 PR 到 master 由你手動做（可以產出 PR 文字）。
- **審查**：只有 `/code-review` 和 `/security-review`，沒有 `/simplify`。先列問題，你選要修哪些。`/security-review` 預設比對 master，所以 skill 會先比較範圍，再讓你選擇。
- **graph**：`graph-yr` 用 codegraph 做即時索引和查詢，另外用腳本產生 `openspec/graph.md`（只支援 Python，不依賴 codegraph），codegraph 的補充放在檔案的 notes 區塊。沒有 codegraph 時自動略過。
- **architect-yr**：附 `references/micro-service-architecture.md`，是事件驅動 micro-service 的參考架構（分層、ack/nack 對照表、一事件一 thread、layer test）。proposal 描述這類 service 時會讀它，可採用、調整或拒絕。既有程式只寫 `architecture.md`，不寫 skeleton。新專案才會核准並安裝套件、選工具（pytest、ruff、mypy）、寫 skeleton 和每個情境一個 skip 的測試。
- **poteto-mode-yr**：新增 Landing playbook，移除 Opening a PR。Bug fix 加核准點，Refactoring 加行為契約確認。
- **優先順序**：poteto-mode-yr 的 playbook 和 `architecture.md` 衝突時，以 playbook 為準，並同步更新 `architecture.md`。playbook 只管流程；程式結構放在 `architect-yr`。
- Landing 時如果 spec 檔案和 `dev` 衝突，可用 `archive-yr` 腳本的 `remerge` 重新套用 delta。
- 入口有 `status.md` 續跑機制：中斷後再執行 `/yr-coding-skills` 會偵測到並問你要不要繼續。

## 注意事項

- 這個包的環境設定假設專案是 Python（venv + requirements.txt）。
- pip proxy：VS Code 的設定不一定被 Claude Code 的 shell 讀到。`repo-setup-yr` 會先測試安裝，失敗就停下來，不會猜 URL。
- `codegraph` 的 CLI 指令我只讀過原始碼，沒有實際執行。skill 會先看 `codegraph --help`，以實際輸出為準。skill 永遠不會執行 `codegraph install`。
- `/code-review` 對分支的比對範圍文件沒寫清楚。`review-pass-yr` 會檢查它回報的檔案是否在 `dev...HEAD` 內，不在的標記為範圍外。
- 沒有 SessionStart hook，也不改 `CLAUDE.md`。路由只靠入口 skill。
